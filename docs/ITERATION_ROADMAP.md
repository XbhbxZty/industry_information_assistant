# 迭代路线图

> **本文档是项目的执行顺序与演进日志**，按"能跑的增量"组织，而非按模块组织。
>
> 配套：[`BADCASES.md`](BADCASES.md)（缺陷记录与修复过程）、[`MIGRATION_PLAN.md`](MIGRATION_PLAN.md)（文件级改动清单）、[`DESIGN_CORE_MECHANISMS.md`](DESIGN_CORE_MECHANISMS.md)（核心机制设计）

## 使用约定（重要）

每轮迭代包含「预期问题」与「实际发现」两栏：

- **迭代 0 已完成**，其中的发现是**真实实测结果**，有数据和提交记录支撑
- **迭代 1 及以后是计划**，「预期问题」是推演，**不得当作已发生的事实对外描述**
- 每轮做完后**回填「实际发现」**，写实际遇到的问题——包括与预期不符的部分。预期错了本身就是有价值的记录

> 这份文档做完就是项目的真实演进史，可直接支撑 README 与面试问答。**它的价值恰恰在于诚实**：编造的演进史经不起追问，真实的演进史每个转折都有据可查。

## 演进主线

```
v0.1 能跑通一次        →  发现输出不可控
v0.2 定义工作流        →  发现模型会编造未知字段
v0.3 反幻觉闸门        →  发现无法判断改进是否有效
v0.4 让它可评测        →  发现缺数据时系统给低风险（危险）
v0.5 风险评分+完整度闸门 →  发现高风险不该全自动放行
v0.6 人机协同          →  倒逼恢复 LangGraph 真实执行
v0.7 性能与成本        →  发现 834s/次不可接受
v1.0 交付形态
```

每个箭头都是一个真实的因果链。这条链本身就是项目叙事。

## 迭代 0：接手与基线 ✅ 已完成

**目标**：搞清楚接手的是什么，能不能跑，问题在哪。

**做了**
- 建专属环境，起 6 个容器，跑通前后端（提交 `e11ea53`）
- 同一问题跑 V1(ReAct) 与 V2(多智能体) 做对照实测
- 通读架构，产出 `DATA_STRUCTURES.md` 阅读路径与 `LEARNING_GUIDE.md`

**实际发现**（真实数据，见 [`V1_VS_V2_BASELINE.md`](V1_VS_V2_BASELINE.md)）

| 发现 | 证据 |
|---|---|
| V1 把源文档占位符当数据写入报告并挂引用角标 | `2019年交易规模达 XX万亿元 ##1$$` |
| V1 反思能识别缺口但生成空查询，回退后命中缓存空转 | 后端日志 `additional_queries: [{}]` |
| V2 收益真实但代价高 | 74s→834s，信源 5→90，报告 1913→8380 字 |
| V2 的 Critic 精确点名了让 V1 栽跟头的信源 | `[critical] hallucination: "原创力文档"非权威机构` |
| **即便 V2 自评也只有 5/10、4 个 critical** | `verdict=needs_revision` |
| Critic 被要求判断时效性却从不注入当前日期 | 把一年前的 2025年4月 判为"未来事件" |
| LangGraph 编排是死代码，实际走手写编排 | `graph.py:349-356` 整段注释 |

**结论**：问题不在"行业选得不对"，而在**输出不可信**。换个行业解决不了任何事。真正值得做的是：在一个不允许幻觉的场景里，把不可信输出治理成可信输出。这直接决定了后续所有迭代的方向。

## 迭代 v0.1：最小闭环 Demo

**目标**：端到端跑通一次企业尽调，**哪怕很粗糙**。先证明路走得通。

**动机**：迭代 0 只验证了原系统能跑行业研究。尽调是不同的任务形态（对象是单一主体、有固定必查项、要求可溯源），得先确认现有 Agent 骨架扛不扛得住。

**范围内**
- 硬编码 1-2 家虚构企业的完整档案（JSON 文件即可，**不建数据库表、不做适配层**）
- 改 Architect / Writer 的提示词，让大纲和报告是尽调形态而非行业研报
- 复用现有 SSE 与前端，能看到过程和最终报告

**明确不做**：数据库建模、数据源适配层、评分卡、评测、前端改造、LangGraph 修复

**预期问题**
- 报告结构每次都不一样，无法横向比较
- 模型会给硬编码数据里**没有的字段**自行编值
- 无法回答"这份报告核实了多少项、漏了多少项"

**验收**：`/research/stream` 传一个企业名，能流式产出一份读起来像尽调报告的东西。

> 关键：这一轮的目的**不是做好，而是快速暴露问题**。做得越糙、问题暴露得越早越好。

## 迭代 v0.2：定义工作流（清单驱动）

**动机**：v0.1 暴露"输出结构不可控、字段随机编造"。根因是**任务被定义成了"自由生成报告"**，而尽调本质是"对一张固定清单逐项给结论"。

**核心改动**：把自由生成翻转为清单驱动（设计见 `DESIGN_CORE_MECHANISMS.md` 第一部分）

```
v0.1：搜索 → 提取 → 写报告            （缺失是静默的）
v0.2：生成必查清单 → 逐项核查 → 写报告  （缺失是显式的）
```

**范围内**
- `state.py` 增 `FieldCheck` TypedDict 与 `field_checks` 字段
- Architect 产出 20 项核查清单骨架（14 必查 + 6 选查）
- Scout 改为逐项取证，填充 status/value/sources
- Writer 按清单逐项渲染

**明确不做**：unverified 的强制约束（下一轮）、评分、评测

**预期问题**
- 模型仍会把取不到的字段填上"合理"的值，因为 prompt 只是"建议"它标未核实
- 清单填充率低，部分字段无从下手
- Writer 可能悄悄跳过状态不佳的字段

**验收**：每次尽调都产出结构一致的 20 项清单，能统计核实率。

## 迭代 v0.3：反幻觉闸门

**动机**：v0.2 证实提示词层面的"请标注未核实"约束不可靠——模型倾向于填一个看起来合理的值。**约束必须从提示词层面提升到架构层面。**

**范围内**
- `unverified` / `conflicting` 作为一等状态，附 `failure_reason`、`attempted_sources`
- Writer 三种状态的**固定渲染模板**，禁止推断、禁止省略、禁止用"暂无"替代"未核实"
- Critic 新增三类检测：`unverified_as_fact` / `conflict_silently_resolved` / `unsupported_risk_conclusion`
- 顺手修迭代 0 发现的日期未注入缺陷（BaseAgent 统一注入当前日期）

**预期问题**
- Critic 会漏检，尤其是隐含断言（"该企业经营稳健"暗示了财务已核实）
- **无法量化改进幅度**——只能凭感觉说"好像好点了"

**验收**：人为构造一个"司法数据源返回空"的用例，报告必须写"涉诉记录未核实"，且绝不出现"无涉诉记录"。

> 这一轮结束时会撞上一堵墙：**改好没有？不知道。** 这就是下一轮的动机。

## 迭代 v0.4：让它可评测 ⭐

**动机**：v0.3 做完无法回答"幻觉率降了多少"。**不能度量就不能改进**——这是整个项目的转折点。

**关键洞察**：要有 ground truth，就必须自己掌控数据。这才是**数据源适配层的真正动机**——不是"因为买不起企查查"，而是**"因为评测需要已知真值"**。

**范围内**
- `service/datasource/` 适配层：抽象基类 + mock 实现（工商/司法/招投标/舆情）
- Stage 1 数据模型落库（`Company`/`JudicialRecord`/`FinancialRecord`/...）
- `scripts/seed_companies.py` 生成 30-50 家虚构企业 + **ground truth 标注**
  - 覆盖优质/一般/高风险/担保圈四类画像
  - **刻意让部分字段"数据源查不到"**，用于测未核实识别
- 评测脚本，四项指标：字段准确率 / **未核实识别率** / 幻觉率 / 等级一致性

**预期问题**
- 首次跑分会很难看，尤其未核实识别率
- 会发现某些字段模型系统性地搞错
- **大概率会发现：数据缺失时系统仍给出乐观结论**

**验收**：`python -m scripts.eval` 输出四项指标表格，可复现。

> 副产品：mock 适配层让任何人 clone 下来无需付费 Key 就能跑通全流程。这解决了作品集项目"面试官跑不起来"的经典问题——但它是评测需求的副产品，不是目的。

## 迭代 v0.5：风险评分与完整度闸门

**动机**：v0.4 的评测**预计会量化暴露最危险的失效模式**——司法数据源查不到 → 三项必查无扣分 → 综合分低 → 输出"低风险，建议授信"。

这是风控上不可接受的："查不到"被当成了"没问题"。

**范围内**（设计见 `DESIGN_CORE_MECHANISMS.md` 第二部分）
- `service/risk_scorecard.py`：五维规则评分，**纯函数、无 LLM、可单测**
- 完整度闸门：核实率 <60% 判"数据不足，无法评级"；司法维度缺项则等级至少中风险；存在冲突项则上调一级
- `triggered_rules` 记录每条规则的触发原因与证据 fact_id

**为什么规则不用 LLM**：评审会要问"为什么是高风险"，答案必须是"资产负债率 82% 超阈值 70%，且有 3 笔被执行"，而不是"模型认为"。且规则可单测、可复现，才能当评测基准。

**预期问题**
- 阈值需要反复调，容易过严或过松
- 闸门可能过于保守，大量案例落到"数据不足"

**验收**：评测中"数据缺失→低风险"的错误清零；每个等级结论都能追溯到规则与证据。

## 迭代 v0.6：人机协同 → 倒逼修复 LangGraph

**动机**：v0.5 有了风险等级后，业务上高风险结论**不能全自动放行**，必须人工确认（合规要求，也是出坏账追责的前提）。

**这一轮的技术转折点**：实现"暂停 → 等人工确认 → 继续"最干净的方式是 LangGraph 原生的 `interrupt`。而**当前 LangGraph 执行路径是被注释掉的死代码**（`graph.py:349-356`）——业务需求倒逼了这次架构修复。

> 这个因果链是真实且有说服力的：不是"我看到死代码手痒重构"，而是"业务要求人在回路，迫使我恢复真正的图执行"。

**范围内**
- 用 `get_stream_writer()` + `stream_mode="custom"` 恢复图执行**同时保留实时 SSE**——这正是原作者当年放弃 LangGraph 的原因，在 langgraph 1.2.x 已有解法（迭代 0 已实测验证 API 可用）
- 删除 `_run_simplified` 中重复的命令式控制流，消除双份实现
- `interrupt` 实现复核卡点；`checkpoint_service` 已支持 `paused` 状态但从无代码设置它，正好接上

**预期问题**
- 恢复图执行后事件顺序/时序可能变化，前端需适配
- interrupt 与项目自有的 checkpoint 机制职责需划清

**验收**：高风险结论触发暂停，前端出现确认卡片，确认后从断点继续；SSE 实时性不退化。

## 迭代 v0.7：性能与成本

**动机**：迭代 0 实测 834 秒/次。业务约束是"业务员在等着回客户"，10 分钟是上限，当前已经贴线。

**范围内**
- Scout 多源检索并行化（当前疑似串行，需先确认）
- 模型路由：字段抽取用便宜模型，风险推理用强模型（`llm_config.py` 已有 per-agent 配置，是现成抓手）
- 全链路 token/耗时/成本埋点，**优化前后对比数据写进 README**
- 失败降级：工具失败、JSON 解析失败、模型拒答

**预期问题**：并行后触发 API 限流；便宜模型在字段抽取上准确率下降——**此时 v0.4 的评测就是安全网**，能直接量化"省了多少钱、掉了多少分"。

**验收**：耗时与成本显著下降，且评测四项指标不明显退化。

> 这一轮能成立，完全依赖 v0.4 建立的评测能力。**没有评测就不敢优化**——这也是"评测必须早做"的实证。

## 与旧计划的映射

原 `MIGRATION_PLAN.md` 按模块分 Stage，仍是**文件级改动清单**的权威来源；执行顺序以本文档为准。主要调整：

| 调整 | 原因 |
|---|---|
| 数据源适配层 Stage 1 → **v0.4** | 真正动机是"评测需要 ground truth"，而非"没有数据" |
| 评测 Stage 5 → **v0.4** | 不能度量就不能改进；后续所有优化都依赖它 |
| 风险评分卡 Stage 2.3 → **v0.5** | 动机应来自评测暴露的真实失效，而非凭空设计 |
| LangGraph 修复 Stage 0.5 → **v0.6** | 由人机协同的业务需求倒逼，因果链更真实；且改动集中在 graph.py 一个文件，晚做不增加返工 |
| 新增 **v0.1 粗糙 Demo** | 先证伪再投入，避免在错误方向上建复杂结构 |
