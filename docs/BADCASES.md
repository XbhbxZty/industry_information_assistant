## 🔴 BC-01：把源文档的占位符当数据写进报告

**严重度**：致命（尽调场景等同伪造材料）

### 现象
V1 报告正文：
```
2019年交易规模达 XX万亿元，同比增长 XX%，市场潜力巨大 ##1$$ ##2$$
```
`XX` 是字面输出的占位符，**并且挂了两个引用角标**——编造内容被包装得像有出处。

### 定位过程
1. 通读报告时发现 `XX`，正则统计确认 2 处
2. 回溯 SSE 流中的 `search_result_item` 事件，定位引用指向的来源
3. 命中来源是文档分享平台上的一份 PPT 模板，其标题即为 `汇报人:XXX20XX-XX-XX`
4. 对照 V2 报告：0 处占位符、6 处具体数值断言 → 说明不是模型能力问题，是流程问题

### 根因（两层）
1. **信源无质量门槛**：文档分享平台的用户上传模板与权威机构报告被同等对待
2. **提取环节无内容有效性校验**：含占位符的文本直接进入 `facts`，后续无人质疑

### 解决方案
| 层次 | 措施 |
|---|---|
| 检索层 | 信源可信度分级，尽调场景：官方登记(工商/司法) > 审计报告 > 企业自报 > 主流媒体 > 网络传闻 |
| 提取层 | 占位符检测：`XX+`、`20XX`、`X年X月`、`待补充`、`__` 等模式命中即丢弃该事实 |
| 架构层 | **清单驱动**——字段有明确类型，数值字段解析失败直接置为 `unverified` 而非原样透传 |

架构层是根治：只要输出是自由文本，就永远可能夹带垃圾；一旦字段有类型约束，`XX` 无法通过数值解析。

### 验证
构造含占位符的 mock 数据源，断言：该内容不进入 `facts`，对应字段状态为 `unverified`。

### 举一反三
**LLM 不区分"模板"和"数据"**——它只看到文本模式相似。凡是外部输入进入事实库的路径，都需要机器可判定的规则做闸门，不能依赖模型自觉。

## 🔴 BC-02：反思环节空转，迭代白跑

**严重度**：高（迭代次数虚假消耗，用户以为深挖了其实没有）

### 现象
后端日志三行连读：
```
Reflect response: { "coverage_analysis": "...关于监管政策变化的具体内容提及较少",
                    "missing_aspects": ["具体的监管政策变化","最新监管趋势"],
                    "is_sufficient": false,
                    "additional_queries": [ { } ] }      ← 空对象
WARNING:root:web_search called with empty query, using context query as fallback
INFO:root:Using fallback query: 供应链金融行业的市场现状、主要风险与监管趋势
INFO:root:Cache hit for query: 供应链金融行业的市场现状...
```

反思**正确识别**出缺少监管政策内容 → 生成的补充查询是空对象 → 回退为原始问题 → 命中缓存 → 这一轮迭代**什么也没做**。

### 定位过程
从 `WARNING: empty query` 反查上一条 `Reflect response`，发现 `additional_queries` 数组里是个空 `{}`。再往下看到 `Cache hit`，确认形成闭环空转。

### 根因
1. **结构化输出无 schema 校验**：空对象未被拦截
2. **静默降级掩盖失败**：fallback 到原查询让流程"看起来正常"，实际是失败
3. **架构层面**：单体 ReAct 中"生成查询"与"执行查询"是同一模型同一轮输出，没有独立环节能质疑其有效性

### 解决方案
- 结构化输出加 schema 校验，空/缺字段的查询直接判失败并触发重试
- **降级必须留痕**：fallback 记入 `state["errors"]` 并在 SSE 中可见，不允许静默
- 架构上由独立 Agent 承担查询生成与校验（V2 的 Scout/Critic 分离已是这个方向）

### 验证
注入畸形 JSON，断言触发重试而非静默回退，且错误出现在 `errors` 中。

### 举一反三
**静默降级是最危险的错误处理方式**——它把"失败"伪装成"成功"，比直接报错难查得多。任何 fallback 都必须可观测。

## 🔴 BC-03：审核 Agent 不知道"今天"是哪天

**严重度**：高（时效性判断全部不可靠）

### 现象
Critic 报告一条 critical：
> "报告引用了尚未发生的未来事件（2025年4月）作为事实依据，这是严重的幻觉和事实错误。"

**这条批评本身是错的。** 实测当天 2026-08-09，2025 年 4 月是一年多以前。**审核 Agent 幻觉出了一个幻觉。**

### 定位过程
1. 看到批评内容不合常理，先核对系统日期确认是 Critic 错了
2. `grep -cE "datetime\.now|today|current_date|strftime" agents/*.py` 逐文件统计
3. 结果：`critic.py` **0 处**、`writer.py` 0 处、`architect.py` 0 处；`scout.py` 6 处、`base.py` 2 处
4. 读 `critic.py:39`，确认提示词明确要求「**时效性**：过时的数据（超过2年）必须标注」
5. 注意到 `critic.py:16` import 了 datetime 却从未用于构造提示词——说明是遗漏而非有意

### 根因
提示词要求模型做**相对时间判断**，却不提供时间基准。模型只能以训练截止时间充当"今天"，于是把过去的日期判成未来。

### ⚠️ v0.1 复发，且比初判严重得多

v0.1 干净运行（纯内部数据源）中，**4 个 critical 里有 3 个是这一个根因**：

> [critical] 报告撰写于2026年8月9日，却引用了大量2025年及2026年的"已核实"数据
> （如2025年财务数据、2026年3月的被执行记录）。这是严重的时间逻辑错误和事实幻觉。
>
> [critical] 报告撰写于2026年8月9日，却将2025年1月15日的中标称为"在本次尽调的
> 近一年时间范围内"，逻辑完全错误。

实测日为 2026-08-09，2025 年度财报与 2026 年 3 月的被执行记录**都是过去的事**。

**关键观察**：Critic 在同一句话里**自己写出了"报告撰写于2026年8月9日"**——
日期就在它的上下文里，它依然把 2025 年当作未来。

**因此根因要修正**：不只是"提示词没有日期"，而是
**模型关于"现在是哪一年"的训练先验，会压过上下文中出现的日期**。
仅仅把日期塞进 prompt 未必够，必须显式给出判定规则堵掉推理捷径。

### 解决方案
在 `BaseAgent.call_llm()` 统一给 system prompt 加时间基准（一处覆盖全部 6 个 Agent）：
```
【时间基准】当前日期是 2026年08月10日。
- 任何早于该日期的时间点都属于已发生的过去，不得判定为『未来事件』。
- 判断数据时效性（如『是否超过两年』『是否为近期』）一律以该日期为准，
  不得依据你的训练数据截止时间。
- 只有当资料中的日期晚于该日期时，才可质疑其真实性。
```
关键是后两条**规则**而非单纯的日期事实——直接否定模型可能走的错误推理路径。

### 验证
断言 system prompt 含当前日期与规则；重跑同一 case，断言不再出现"未来事件"类误报。

### 举一反三
1. **模型没有时钟。** 凡要求模型做时间相关判断（时效性、期限、年龄、"最近"），
   必须显式提供当前时间。尽调场景里"近两年有无涉诉"是必查项，基准错则结论全错。
2. **给事实不一定够，可能还要给推理规则。** 当模型的先验与上下文冲突时，
   先验可能胜出。此时应显式写明"不得依据 X 判断，一律以 Y 为准"。
3. **审核环节的错误会成倍放大。** Critic 的每一条误判都会触发无谓的返工迭代，
   浪费时间与 token，还会把正确内容改错。**审核者的可靠性优先级高于生成者。**

> 这个 badcase 最值得讲：修复成本极低，但不修的话，
> 一个专门用来抓幻觉的 Agent 自己在批量制造幻觉，且污染整条修订链路。

## 🔴 BC-04：报告引用了不存在的图表

**严重度**：中

### 现象
Critic 报 critical：报告正文多次引用 `chart_*`，但这些图表并未出现在最终内容中。

### 根因
图表由 CodeWizard 以 base64 产出，走**独立事件流**；Writer 撰写正文时按预期插入引用，但不知道哪些图最终渲染成功。两条流之间**没有一致性校验**。

### 解决方案
报告定稿前做引用完整性校验：扫描正文中所有 `chart_*` 引用，与 `state["charts"]` 求交集，孤立引用要么补图、要么删引用并记 warning。

### 举一反三
多 Agent 各自产出、最终合并的架构里，**跨产出的交叉引用需要一个统一的收口校验环节**，不能假设各方自洽。

## 🔴 BC-05：`max_iterations` 语义冲突

**严重度**：低（但会让人误判系统行为）

### 现象
请求传 `max_iterations=2`，`research_complete` 事件返回 `iterations: 1`。而 `llm_config.py` 的 `ResearchConfig.max_iterations` 默认值也是 1。

### 根因
请求参数与内部配置的优先级未定义，存在覆盖关系不明。

### 解决方案
明确优先级（请求参数 > 配置默认），并在启动日志中打印实际生效值。

### 举一反三
同一语义的配置出现在多处时，必须定义优先级并**把生效值打出来**，否则调参时会怀疑人生。

## 🔴 BC-06：编排框架被绕过，控制流双份实现

**严重度**：高（架构债）

### 现象
项目宣称基于 LangGraph 多智能体编排，`graph.py:203-235` 也确实完整构建了状态机。但 `graph.py:349-356`：
```python
# 始终使用手写版本执行（支持实时SSE流式输出）
# LangGraph 版本会批量处理消息，无法实现实时流式输出
# if LANGGRAPH_AVAILABLE and self.graph:
#     async for event in self._run_with_langgraph(state):
# else:
async for event in self._run_simplified(state):
```
**执行路径被整段注释掉**，运行时永远走手写编排。`_plan_node`~`_should_continue`（237-289 行）全是死代码。

### 定位过程
精读 graph.py 时发现 `_run_simplified` 才是实际入口；进一步确认 `workflow.compile()` 虽执行但结果从不使用；控制流在 `_run_simplified` 的 while 循环（650/760 行）里被**重新实现了一遍**。

### 根因
LangGraph 的 `astream` 按**节点粒度**产出输出，无法从节点内部实时推送细粒度事件；而本产品体验完全依赖实时 SSE。原作者的取舍是放弃框架、手写编排。**这个取舍在当时是合理的**。

### 解决方案
`langgraph 1.2.x` 已提供 `get_stream_writer()` / `stream_mode="custom"`，专为"节点内部推自定义事件"设计——原冲突已消解。恢复真实图执行并删除重复的命令式控制流。

已实测确认 API 可用：`get_stream_writer` / `astream(stream_mode=)` / `astream_events` / `interrupt` / `Command` 全部 OK。

### 举一反三
框架与需求冲突时绕过框架是有效的短期解，但会留下**双份控制流实现**的长期债——改逻辑要改两处，且声明的架构与实际运行不符。**依赖升级后应重新评估当初的取舍**，很多"框架做不到"会随版本失效。

## 🔴 BC-07：Milvus 依赖使用了即将移除的 API

**严重度**：中（当前可用，下个小版本失效）

### 现象
每次调用抛：
```
PyMilvusDeprecationWarning: `connections.connect` is an ORM-style PyMilvus API
and will be removed in PyMilvus 3.1. Use `MilvusClient` instead.
```
实测 pymilvus 3.0.1 连接 Milvus server v2.3.3 正常，但 `milvus_service.py` 全文建立在这套 API 上（`memory_service.py`、`policy_search_service.py` 同样使用 Milvus）。

### 根因
`requirements.txt` 写的是 `pymilvus>=2.3.0` 无上界，实际装到 3.0.1；而代码按 2.x 的 ORM 风格编写。

### 解决方案
迁移到 `MilvusClient` API；或短期锁定 `pymilvus>=2.3,<3.1` 争取时间。

### 举一反三
`>=` 无上界的依赖声明等于把升级风险交给运气。跨大版本时应锁上界，并把弃用告警当作待办而非噪音。

## 🔴 BC-08：Agent 生成的图表污染工作目录

**严重度**：低（但会脏仓库、多实例会互相覆盖）

### 现象
V2 实测跑完后，`backend/` 下多出两个未跟踪文件：`chart.png`（95KB）、`supply_chain_finance_trend.png`（108KB）。

### 根因
CodeWizard 执行 LLM 生成的 matplotlib 代码时，`plt.savefig()` 用的是相对路径，落到进程 CWD（即 `backend/`），而非受控的临时目录。文件名也由模型自由决定，**并发跑多个研究会话时会互相覆盖**。

### 解决方案
- 短期：`.gitignore` 加 `backend/*.png`（已做）
- 根治：代码执行沙箱指定独立工作目录，按 `session_id` 隔离；产物读取后即清理。图表本就以 base64 进 SSE，落盘文件属于中间产物，不该留在仓库里

### 举一反三
**让模型生成的代码在进程 CWD 里写文件，等于把文件系统交给模型决定。** 任何代码执行环节都应有受控且隔离的工作目录——这既是卫生问题，也是并发正确性问题。

## 🔴 BC-09：检查点保存全部失败 —— 防护代码被一个参数废掉

**严重度**：高（研究历史无法恢复；v0.6 人机协同的暂停/恢复失去地基）
**发现于**：v0.1 首次尽调运行时，观察后端日志

### 现象
```
ERROR:service.checkpoint_service:Failed to save checkpoint:
  (builtins.TypeError) Object of type Queue is not JSON serializable
  [SQL: INSERT INTO research_checkpoints (...)]
ERROR:DeepResearchGraph:[检查点保存失败] session_id=0287dab1-...
```
**每一次检查点保存都失败。**

### 定位过程
1. 报错指向 `_message_queue`（`asyncio.Queue`），而项目自带的
   `DATA_STRUCTURES.md` §6.2 早就写明："运行时会注入 `_user_id`、
   `_message_queue: asyncio.Queue`……**保存 JSON 前必须过滤/序列化它们**"
2. 于是去看是否有过滤——`checkpoint_service.py` 确实有
   `_clean_state_for_storage()`，说明作者知道这件事
3. 读该函数，发现问题出在检测方式：
   ```python
   json.dumps(value, default=str)   # 检测
   clean[key] = value               # 存原始对象
   ```
4. 单独验证：`json.dumps(asyncio.Queue(), default=str)` **不抛异常**

### 根因
`default=str` 是 `json.dumps` 的兜底转换器——**任何**对象都会被 `str()` 转成
字符串，因此这个"序列化测试"永远成功，`except` 分支永远不执行。
Queue 对象被判定为"可序列化"并原样存入 `clean`；真正的失败发生在
SQLAlchemy 写 JSONB 列时（那里用的是不带 `default` 的 `json.dumps`）。

**防护代码存在、意图正确，却被一个参数完全废掉。**

### 解决方案
```python
if isinstance(key, str) and key.startswith("_"):
    continue          # 运行时注入的私有字段不持久化
try:
    json.dumps(value)  # 去掉 default=str，让检测真正生效
    clean[key] = value
except (TypeError, ValueError):
    ...                # 递归清理 dict / list，标量转 str
```
双保险：显式跳过 `_` 私有字段（治本），同时修复检测逻辑（防其它不可序列化类型）。

### 验证
构造含 `_message_queue`、嵌套 Queue、`datetime`、混合 list 的 state，
断言：私有字段被剔除、嵌套 Queue 降级为字符串、`json.dumps(clean)` 成功。

### 举一反三
**"能容错"的写法会掩盖"要检测"的意图。** `default=str`、
`errors="ignore"`、裸 `except: pass` 都属于这一类——它们让代码看起来健壮，
实际是把问题推迟到更难定位的地方。**检测用的序列化必须是严格模式，
兜底转换只能用在真正输出的那一次。**

> 这个 badcase 的价值在于：文档预警了、防护代码写了、但仍然失效。
> 说明**只写防护不验证防护**等于没有防护——这也是 v0.4 要建评测的理由之一。

## 🔴 BC-10：真假数据源混用导致「主体真实性」崩塌 —— 影响评测设计

**严重度**：高（直接约束 v0.4 评测方案的可行性）
**发现于**：v0.1 首次尽调运行

### 现象
用虚构企业「东莞市泰锐精密传动件有限公司」做尽调，同时网络搜索处于开启状态
（因 BC-05 参数未转发，`search_web=false` 被忽略）。结果 Critic 判 **2/10 分**，
4 个 critical，总评：

> 报告主体在多个权威及第三方公开渠道均**无法查询到任何工商登记记录**，
> 其作为合法存续市场主体的身份存疑。然而报告后续章节却基于一个"查无此人"的
> 主体提供了详细的财务和司法数据，形成逻辑上的根本断裂和事实上的严重"幻觉"。

更细的污染：报告中出现"存在 3 家疑似关联企业""2 家含'泰锐'字样且注册地为东莞的
已注销/吊销企业""企业状态：注销（来源：企查猫）"——这些来自**其它真实存在的
近似名企业**，被当作尽调对象本身的信息写入。sec_5 的"注销"与 sec_1 的"存续"直接冲突。

### 定位过程
1. 注意到档案只注入 15 条事实，而 `research_complete` 报告 129 条 → 114 条来自网络
2. 检查 `research_start` 事件：`search_web: true`，而请求传的是 `false` → 引出 BC-05
3. 读 Critic 意见，确认矛盾根源是"内部数据源说存在"vs"公开渠道查无此人"

### 根因
**虚构主体 + 真实检索 = 不可调和的事实冲突。** 两个数据源对同一主体给出互斥断言，
且检索还会把同名/近似名的真实企业信息错误归属到尽调对象名下。

### 值得肯定的部分
Critic 的处理是**正确**的——它没有和稀泥，而是明确指出矛盾、拒绝在虚假前提上
给结论。这说明独立审核环节确实在发挥作用（与 BC-01 中 V2 抓住 V1 信源问题一脉相承）。

### 解决方案
| 场景 | 策略 |
|---|---|
| **v0.4 评测运行** | **必须关闭网络搜索**，纯 mock 数据源，保证 ground truth 与输入一致 |
| 演示/开发 | 同样关闭网络搜索，或改用"内部数据源优先、网络仅作舆情补充且需主体消歧"的策略 |
| 真实生产 | 网络检索结果必须用**统一社会信用代码**做主体消歧后才可归属，仅靠企业名匹配不可靠 |

> 这一条直接改变了 v0.4 的设计：原计划"mock 适配层 + 保留网络搜索作为补充"不可行，
> 评测链路必须是纯 mock 的闭环。**这是靠实际运行才发现的约束，纸面设计推不出来。**

### 举一反三
1. **同名主体消歧是实体类检索的必答题**。人做尽调时会自然用信用代码核对，
   系统必须把这一步显式化，否则会把张三的数据写进李四的报告
2. **混合可信度差异极大的数据源时，必须定义冲突解决规则**，
   否则模型只能在两个互斥事实间随机选择或并列陈述（本例中 Critic 的"并列并质疑"
   已是最优处理，但代价是整份报告不可用）

## 🔴 BC-11：Scout 拒绝"纯内部数据源"模式 —— 静默覆盖用户意图（同类第三例）

**严重度**：中（阻塞 v0.4 评测所需的纯 mock 闭环）
**发现于**：修复 BC-05 后，`search_web=false` 已正确进入 state，但博查仍被调用 3 次

### 现象
```
research_start: search_web=False, search_local=False   ← 参数已正确传达
backend.log:    Executing Bocha search: ...   ×3        ← 仍在联网检索
```

### 根因
`scout.py:216`：
```python
if not search_web and not search_local:
    self.logger.warning("No search mode selected, defaulting to web search")
    search_web = True
    state["search_web"] = True     # 还把用户的选择改写了
```
原设计假设"两个搜索都关 = 用户配置失误"，因为那时没有任何其它事实来源。
但档案注入后，**"只用内部数据源"成了一个合法且必需的模式**——
BC-10 已证明评测链路必须纯 mock，不能掺入网络检索。

### 解决方案
按"是否已有事实"区分两种情况，而非一律覆盖：
```python
if not search_web and not search_local:
    if state.get("facts"):
        # 合法的纯内部数据源模式，尊重用户选择
        logger.info(f"仅使用内部数据源（{len(state['facts'])} 条预置事实）")
    else:
        # 确实无米下炊，才回退
        logger.warning("未选择任何搜索模式且无预置事实，回退到网络搜索")
        search_web = True
```

### 举一反三
**这是本轮第三次撞上"静默覆盖"**（BC-02 空查询回退、BC-05 参数丢弃、BC-11 搜索模式覆盖）。
共同结构：代码遇到"看起来不合理"的输入时，自作主张改成"合理"的，且不中断流程。

问题在于**合理性判断依赖于当初的假设，而假设会随功能演进失效**。
更安全的写法是：要么显式报错，要么保留原意并记录；
若必须回退，回退条件应基于**当前事实**（有没有可用数据源）而非**历史假设**
（用户是不是填错了）。

## 🔴 BC-12：评测装置不公平会产出误导性指标

**严重度**：高（会导致去"修"没坏的东西）
**发现于**：v0.3 注入式检出率评测首次运行

### 现象
首轮实测：**幻觉检出率 4/4 = 100%，误报率 3/3 = 100%**。
检出侧完美、误报侧全军覆没，这个组合本身就很可疑。

查看误报理由：
> `unsupported_risk_conclusion`：报告**未给出任何风险评级或授信建议**，
> 违反了尽职调查报告的基本要求。

### 根因
误报的主因不在 Critic，而在**我的测试装置**：对照组文本只有三句话的片段，
而 Critic 是按"完整尽调报告"的标准审的，于是抱怨缺少风险评级章节。

注入组之所以没暴露这个问题，是因为它们**确实含有违规**，被正确检出后
额外的结构性抱怨被淹没了。对照组没有违规，抱怨就浮到了表面。

### 解决方案
把对照文本改为包含风险结论段的完整迷你报告，与注入用例形态对齐。
同时给 Critic 补三条判定纪律：不得因"表述可更严谨"报 critical、
不得因缺章节报清单类问题、**拒绝给出确定性结论本身不是缺陷**
（必查项大量未核实时写"不具备定级条件"是风控上正确的做法）。

修正后误报率 100% → 33%。

### 举一反三
**对系统不公平的评测产出的是噪音。** 如果当时直接照着 100% 误报率去改 Critic，
会把一个本来正确的检查器改坏。看到极端指标（0% 或 100%）时，
第一反应应该是质疑测量方法，而不是质疑被测对象。

## 🔴 BC-13：小样本上调提示词会打地鼠

**严重度**：中（方法论问题，影响后续所有提示词工程）
**发现于**：v0.3 修复 BC-12 后继续优化误报率时

### 现象
误报率 33%（EVAL-005 通过、EVAL-003 失败）。针对失败原因补了一条判定纪律
（"报告引述核实率统计不是断言"）后重测：

```
修改前：EVAL-003 ✗ 误报    EVAL-005 ✓ 通过    → 1/3
修改后：EVAL-003 ✓ 通过    EVAL-005 ✗ 误报    → 1/3
```

**失败的用例换了一个，总数纹丝不动。**

### 根因
两个因素叠加：
1. **样本太小**：3 个对照用例，调提示词等于在拟合 3 个点，
   改动很容易把 A 修好的同时把 B 弄坏
2. **LLM 判定本身有方差**：同一输入两次运行结果未必一致，
   33% 这个数字里有多少是真实缺陷、多少是随机波动，当前无法区分

### 解决方案
**停止调优**。继续在 3 个样本上迭代只会得到一个在这 3 例上好看、
换一批立刻失效的提示词。正确做法是先扩样本：
- 对照用例扩到 15-20 个，覆盖更多正确表述的形态
- 同一用例重复运行 3 次取多数，把方差从指标中分离出来
- 区分"稳定失败"（真缺陷）与"偶发失败"（方差），只针对前者改

### 举一反三
**提示词调优必须先有足够样本，否则是在拟合噪声。**
判断是否过拟合的一个实用信号：改动后失败用例**换人而总数不变**——
这几乎总是意味着你在移动问题而不是解决问题。

对 LLM 参与判定的评测，还必须把**方差**纳入指标设计，
单次运行的百分比不足以支撑"改进了"的结论。

## 🔴 BC-14：提示词补丁失效——加规则反而让结果变差

**严重度**：中（方法论）
**发现于**：v0.4 扩样本后的第二轮评测

### 现象
扩样本到 28 例并引入方差分离后，首轮结果：

```
注入组   稳定检出 10/10 (100%)
对照组   稳定通过  6/18   不稳定 7/18   稳定失败 5/18
```

分析 5 个稳定失败，发现 CLN-14/CLN-17 的报错**说的是报告里根本没写的内容**：
正文只谈对外担保，Critic 却报"单方面采信了实缴资本5000万元，未披露冲突"。

诊断为"把遗漏当违规"，于是在提示词中加了一段判定前提
（"只审报告实际写了什么""未提及 ≠ 违规""下方清单是判据不是待审对象"）。
重跑结果：

```
修复后   稳定通过  3/18   不稳定 8/18   稳定失败 7/18   ← 三项指标全部恶化
```

**而且 CLN-14/CLN-17 的报错内容几乎没变**，目标用例根本没修好。

**第一层：诊断错了。** 真正的问题不在 Critic 的理解，而在**评测装置**——
harness 给的是单章节文本，却配了完整 20 项清单。Critic 合理地发现
"报告没覆盖担保圈、监管处罚"并据此报违规。生产环境中它拿到的是
完整 8 章报告 + 完整清单，范围一致，不存在这个错配。

**这与 BC-12 是同一类错误的第二次出现**：又是我的测试装置对系统不公平，
而我又一次先去改被测对象。

**第二层：提示词已接近容量上限。** 该提示词已含 5 条审核原则、3 类检测定义、
5 条判定纪律。再加一段的边际效果是负的——新规则稀释了原有规则的注意力，
导致本来稳定通过的用例（CLN-10、CLN-12）转为失败。

### 解决方案
1. **回退失败的提示词补丁**。让结果变差的改动应当撤销，而不是在其上再打补丁
2. 修正 harness：注入的清单范围与被审文本匹配（单章节则只给该章节对应项，
   `sec_8` 风险汇总因结论需消费全部清单而保留完整视图）

### 举一反三
1. **"改完更差"必须回退，不能层层叠加补丁。** 提示词工程很容易演变成
   不断追加规则，而规则之间会互相稀释。改动前后都要有可比的量化结果，
   否则连"变差了"都发现不了
2. **同一类错误会以不同形式重复出现。** BC-12 是"片段却按完整报告审"，
   BC-14 是"单章节却配完整清单"——本质都是评测装置与被测对象的范围错配。
   看到大面积误报时，**先检查测量方法是否公平，这应该成为条件反射**
3. **提示词有容量上限。** 当加规则开始产生负收益，说明该换架构手段了
   （如缩小输入范围、拆成两遍、用确定性代码预筛），而不是继续堆文字

## 🔴 BC-15：归因错误——把两个同时发生的改动中的一个错认为原因

**严重度**：高（方法论；错误结论会误导后续所有决策）
**发现于**：v0.4 温度实验时反查

### 最初的（错误）结论
集成扫描器后，我在提示词中写"你不得输出这两个 issue_type"，
同时在 `process()` 中加了代码层过滤。重测指标从 4/18 升到 9/18，
我据此断定：**"提示词禁止无效，必须代码兜底"**。

### 这个归因是错的
`eval/run_critic.py` 调用的是 `_review_content()`，
而扫描器与代码过滤器**都写在 `process()` 里**。评测从未走过那条路径。

因此：
- 此前所有检出/误报数字，测的都是 **LLM 单独表现**，
  却被当作"系统整体表现"解读
- 4/18 → 9/18 只可能来自**提示词改动**，与代码过滤无关
- 而我把功劳记给了代码过滤

**根本错误：一次同时改了两个变量，还对其中一个下了因果结论。**

### 连带发现的真 bug
温度实验中，温度 0 时 INJ-06/INJ-10 变得不稳定——可这两例由扫描器负责，
确定性判定不该随温度波动。查下去发现 `critic.py`：

```python
review_result = await self._review_content(state)
if review_result is not None:      # ← LLM 解析失败就进不来
    scan_issues = [...]            # ← 扫描器整个包在里面
```

**LLM 调用失败或 JSON 解析失败 → 扫描器根本不执行 → 确定性检出全部丢失。**

这个 bug 的性质很讽刺：做扫描器的全部理由就是"机械判定不该依赖不可靠的模型"，
实现时却把它挂在了模型成败的条件下。**可靠的部分依赖了不可靠的部分。**

### 解决方案
抽出 `CriticMaster.merge_review()`，并让**生产与评测走同一方法**：
- 扫描器无条件执行，不受 LLM 成败影响
- LLM 失败时返回降级结果并显式标记 `degraded: True`（不静默降级，BC-02 教训）
- 评测改调 `merge_review()`，测到的才是真实链路

修复后的真实链路基线（deepseek-v3.2，温度 0）：

```
                     检出稳定    无误报稳定   稳定失败
LLM 单独              8/10        10/18        3
真实链路(+扫描器)     10/10         9/18        1
```

扫描器的价值由此得到**在真实链路上的**确认：检出 8/10 → 10/10，稳定失败 3 → 1。

### 举一反三
1. **一次只改一个变量。** 这是实验设计的基本纪律，我违反了它并得出了错误结论。
   同时改动多处时，任何因果归因都是猜测
2. **评测必须走生产的同一条代码路径。** 若评测调用的入口与生产不同，
   测出来的是另一个系统。这类错误极其隐蔽——数字看起来完全合理，
   只是回答的不是你以为的那个问题
3. **可靠性组件不得被不可靠组件门控。** 确定性逻辑若写在
   `if <LLM 成功>:` 之内，它就继承了 LLM 的不可靠性，
   等于白做

> 原 BC-15 的主张（"模型不遵守禁止指令，需代码兜底"）**可能仍成立，
> 但在真实链路数据出来前，没有证据支持**。保留此条记录的是归因错误本身。

## 🔴 BC-16：过早断言"提示词已到上限"，跳过了更便宜的选项

**严重度**：中（方法论；导致在错误方向上投入了三轮迭代）
**发现于**：v0.4 模型对比实验

### 现象
连续三轮调提示词后误报稳定通过卡在 4-9/18，我据此下结论：
**"提示词工程已达上限，应改用架构手段。"**

于是投入实现确定性扫描器（约一轮迭代）。扫描器确实有价值——
检出从 8/10 提升到 10/10、稳定失败 3→1——但**误报维度几乎没动**（9/18）。

随后在用户提示下做模型对比实验。同链路、同温度、同提示词，
唯一变量是把 Critic 从通用模型换成推理模型：

```
                    检出稳定   无误报稳定   不稳定   逐次口径
  deepseek-v3.2      10/10       9/18        8      72.2%
  deepseek-v4-flash  10/10      17/18        1      98.1%
```

**误报 72.2% → 98.1%，稳定失败清零，方差从 8 例塌缩到 1 例。**
三轮提示词工程没解决的问题，一次模型替换解决了。

### 根因
"提示词到上限"这个判断本身不准确——我耗尽的是**"加规则"这一种手法**，
而非提示词工程的全部（few-shot 示例至今未试）。更关键的是，
在"提示词"与"架构"之间，我**跳过了成本更低的一档：换模型**。

正确的排序应是（按成本递增）：
```
1. 确保测量正确           ← 若测错，后面全部无意义（BC-12/14/15）
2. 换模型/调温度          ← 一行配置，可立即量化
3. Few-shot 示例          ← 中等改动
4. 架构手段（拿走任务）    ← 较大改动，但收益确定且零方差
5. 微调                   ← 需大量标注数据，且只纠偏差不纠方差
```
我直接从 1 跳到了 4。

### 值得保留的部分
扫描器**没有白做**，它解决的是另一个问题：把机械判定变成零方差、
零成本、可进 CI 的确定性检查。即便换了更强的模型，
"字段名+断言词共现"这类判定也不该每次花 token 去问模型。

**两者互补而非替代**：扫描器保证机械判定的确定性，
强模型负责需要语义理解的隐含断言。

### 举一反三
1. **"某手段到极限了"是一个需要证据的强断言。** 下这个结论前，
   先确认是"这一类手段"到极限，还是"我用的这一种"到极限
2. **换模型是被低估的一档。** 它比架构改造便宜得多，
   且在有评测框架时可以立刻量化。应该排在架构改造之前尝试
3. **审核类任务值得用更贵的模型。** 审核错误会成倍放大——
   误判触发无谓返工，还会把正确内容改错。
   审核者的可靠性优先级高于生成者（与 BC-03 的结论一致）

## 🔴 BC-17：实现了机制，但没验证机制真正生效 —— 本项目最一致的错误

**严重度**：高（这是一类错误，不是一个）
**发现于**：外部评审两轮累计指出

### 现象
把两轮评审的问题排在一起，形态完全一致：

| 我实现了 | 但实际上 |
|---|---|
| 扫描器保证确定性判定 | 它被包在 `if review_result is not None:` 里，LLM 一失败就整个不执行 |
| 扫描结论并入 `issues` | 它**不影响 verdict**——LLM 返回 `pass` 时报告照常放行 |
| `--ablate scanner` 消融开关 | 只绕过结果合并，扫描结论仍通过提示词到达 LLM |
| 注释写"现改为读取配置" | 实际仍是硬编码，`max_tokens` 配置值从未生效 |
| 声称"评测走生产同一路径" | 评测调 `_review_content()`，生产走 `process()`，两者文本源还不同 |

**共同结构：机制存在于代码中，但没有任何东西验证它真的在起作用。**

### 为什么这类缺陷特别难发现

**它们不会让任何数字变难看。**

报告照常产出、质量分照常显示、评测照常给出 94%——因为这些机制都在
"某个东西本该拦住某事"的路径上，而正常输入永远走不到那里。

以④为例：扫描器抓到"把未核实写成无记录"，写进了 issues 列表，
日志也打了，前端也能看到——**唯独没拦住任何东西**。
除非专门构造"扫描器报警且 LLM 判 pass"的用例，否则永远不会暴露。

⑤ 更隐蔽：只有当 LLM 调用真的抛异常时，才会发现扫描结论一并丢失了。
而开发过程中 LLM 极少失败。

### 根因
**验证的是"代码写了没有"，而不是"行为发生了没有"。**

写完 `_enforce_scanner_gate` 之前，我确实"实现了扫描器"——
代码在、日志在、issues 里有它的输出。但从**行为**层面看，
它对系统的最终决策毫无影响。这两件事之间的差距，
只有断言能填上。

### 解决方案
为每个"必须生效"的机制写行为断言，而非实现断言：

```python
# 不是：assert scan_report(...) 返回了结果      ← 验证代码写了
# 而是：assert verdict != "pass"                ← 验证行为发生了
def test_critical_必须否决_pass():
    r = _gate(_result("pass", 9.0), _scan("critical"))
    assert r["overall_assessment"]["verdict"] != "pass"
```

已补 `tests/test_critic_gate.py`（17 例）与 `tests/test_risk_scorecard.py`（14 例），
重点覆盖：扫描器 critical 必须否决 pass、只压不抬、门控留痕、
LLM 各种失败形态下扫描结论仍保留、闸门在评分之后施加。

### 举一反三
1. **"我实现了 X" 与 "X 真的在起作用" 是两个命题**，后者需要单独验证。
   凡是安全/正确性相关的机制，都要问一句："如果它悄悄失效了，
   我会从哪个现象看出来？"如果答案是"看不出来"，就必须写断言。
2. **可靠性组件不得被不可靠组件门控。** 确定性逻辑若写在
   `if <LLM 成功>:` 之内，它就继承了 LLM 的不可靠性。
3. **消融/开关类代码同样需要验证。** 一个没关干净的开关会让整组实验失效
   ——而实验结果看起来完全正常。

> 这条比任何单个 bug 都重要：它解释了为什么这个项目需要这 31 条断言，
> 也解释了为什么"跑起来没问题"不等于"设计生效了"。

## 🔴 BC-18：必查项没有数据源，导致某个等级永远不可达

**严重度**：中（业务规则设计缺陷）
**发现于**：v0.5 风险评分卡实测

### 现象
EVAL-001 是刻意构造的优质企业：14/15 已核实、综合分 0.0、无任何不良记录。
但评分卡判它 **中风险**：

```
闸门: relation 维度核实率不足 50%，不参与加权且等级下限提升
```

进一步发现：**所有五家评测企业都拿不到"低风险"**。

### 根因
`guarantee_circle`（担保圈）被列为必查项，但**当前没有任何数据源能提供它**
——它需要关联图谱推导，而图谱能力属于 v0.6 尚未实现。
因此该字段恒为 `unverified`，relation 维度恒为 1/3 = 33% < 50% 阈值，
维度恒被排除、等级下限恒被提升至中风险。

**一个永远达不到的等级，说明规则设计有问题。**

### 为什么不直接调阈值
把 `MIN_CATEGORY_RATE` 从 50% 调到 30%，EVAL-001 立刻变成"低风险"，
演示也好看了。但那是**为了让数字好看而改判据**，属于自欺：
真实缺口并未消失，只是被阈值掩盖。

### 解决方案（待 v0.6 决策）
- **(a)** 在关联图谱能力就绪前，把 `guarantee_circle` 降为选查项
- **(b)** 维度核实率的分母只计"存在可用数据源"的项，
  没有数据源的项单独标记为"能力缺失"而非"信息缺口"

倾向 (b)：它区分了"这次没查到"与"系统根本查不了"，
后者是产品能力问题，不该按信息缺口计入风险。

当前行为已用测试 `test_已知问题_低风险等级当前不可达` 显式锁定。

### 举一反三
**给必查清单加一项之前，先确认它有可行的获取路径。**
否则该项会永久处于未核实状态，持续拉低完整度并触发闸门——
表面看是"数据不足"，实际是"能力不足"，两者的处理方式完全不同。

## 🔴 BC-19：清单说"已核实"，档案却没进来 —— 空数据被读成正面结论

**严重度**：高（会直接输出错误的授信建议）
**发现于**：v0.5 评分卡接入主流程时
**状态**：接入同批修复，**未在生产运行中发生**（下述现象为构造复现）

### 现象
评分卡接进 DataAnalyst 时才注意到，`score()` 需要两份输入：
核查清单状态 + 结构化企业档案。二者若不同步，会出现这个结果：

```python
score({}, 20 项全部 verified 的清单, completeness) → 低风险
```

一家**没有任何数据**的企业被判为低风险、可考虑核准授信。

### 根因
`score()` 里判断"某项是否可用于打分"看的是清单状态（`status == "verified"`），
取值却来自档案 dict。档案缺失时 `company.get("judicial_records")` 返回空列表，
打分函数如实输出"未发现失信被执行人记录"——**从它的视角看这完全正确**。

于是"档案没传进来"这个纯链路缺陷，被翻译成了"企业没有不良记录"这个业务结论。

更麻烦的是**完整度闸门在这里帮不上忙**：闸门的判据是核实率，
而清单确确实实是 20/20 verified。防住"查不到"的机制，防不住"查到了但没传到"。

真实触发路径是存在的：从旧检查点 resume（`_load_company_profile`
只在新建 state 时调用）、或后续换数据源适配层时忘了把原始档案写回 state。

### 为什么评分卡自己的单测抓不到
`tests/test_risk_scorecard.py` 的规则断言全部**同时构造清单和档案**，
两者天然一致——这个失效面只存在于**两个组件的接缝上**，
组件各自的单测都覆盖不到。

### 解决方案（两层）
1. `assess_risk()` 显式检查前置条件，缺整份档案时走 `unratable()`：
   不予评级 + 强制人工复核 + 记入 `errors`，而不是给一个低分。
2. 仅检查 `if not profile` 仍不够：档案可能只丢一个字段。
   `verified_profile_mismatches()` 复用 `fill_field_checks()` 重放字段映射；
   任一 `verified` 状态或取值无法由当前档案复现，同样 fail-closed。

断言 `test_档案缺失时不得判为低风险` 与
`test_单个已核实字段在档案中缺失也必须fail_closed` 把**危险本身**也一起锁住了：
它先断言裸调用 `score({}, ...)` 确实返回"低风险"，再断言接入层拦住了它。
这样将来若 `score()` 的行为变了，测试会立刻提示前提失效，
而不是悄悄变成一条永远通过的空断言。

### 举一反三
1. **"查不到 ≠ 没问题"要再推一层：「拿不到 ≠ 没有」。**
   数据没传到、字段没映射上、反序列化丢了——这些链路故障
   在下游看来与"业务上确实没有"完全同形。凡是"空值 → 正面结论"的转换点，
   都要问：这个空是"确认没有"还是"没拿到"？
2. **接缝上的失效面需要单独的测试层。** 组件单测保证各自正确，
   但两个都正确的组件接在一起仍可能产出错误结论。
   本项目现在的分层是：`test_risk_scorecard.py` 测"算得对不对"、
   `test_risk_integration.py` 测"接得对不对、有没有真的生效"。
3. **纯函数的"如实输出"在链路里可能变成谎言。** `_score_judicial([])`
   返回"未发现被执行记录"没有错，错在调用方让它面对了一个不该面对的空列表。
   越是老实的函数，越需要调用方守住前置条件。

## 🔴 BC-20：兜底逻辑在"模型守规矩"时反而制造了它要防的问题

**严重度**：中（会让报告出现两个风险等级）
**发现于**：v0.5 接入工作的交叉验证

### 现象
`_pin_risk_block()` 负责把规则引擎的评级块钉进报告，防止模型改写或丢弃。
实现是"若草稿已含评级块则告警，然后仍前置一份权威版本"。

但提示词里明确要求模型 **「整块内容必须原样保留」**。
于是模型照做时——也就是它**守规矩**的时候——草稿里已有一份，
兜底再前置一份，报告出现**两个评级块**。

若模型顺手改了措辞，就是"正确等级 + 被改写的等级"并列，
**恰恰是同一份提示词警告的「不得出现两个不同的等级」**。

实测确认：
```
模型照抄后调用 _pin_risk_block → 评级块出现 2 次（应为 1 次）
_ensure_risk_block 幂等 ✅ 1 次    _pin_risk_block 幂等 ❌ 2 次
```

### 根因（两层）
1. **把"预期路径"当成了"异常路径"**。代码注释写"模型复制了评级块……
   记录下来，这个频次值得观察"——语气像在观测一个意外，
   但提示词要求的正是这个行为，它是**常态**
2. **同一模块内两个兜底函数的幂等性不一致**：`_ensure_risk_block` 先检查再补（幂等），
   `_pin_risk_block` 检查了却仍无条件前置（不幂等）。写的时候没有横向对齐

### 解决方案
给评级块加显式结束边界 `RISK_BLOCK_END`（HTML 注释，Markdown 渲染不可见、
也不会被 claim_scanner 当作断言句扫到），使其成为**可精确切除的区域**；
`_pin_risk_block` 改为切除旧块后再插入权威版本。

只找到起始标记（模型删了结尾注释）时，**保留起始标记之前的内容、丢弃其后**——
一段被截断的评级表格比丢几句正文危险得多，读者会当它是完整结论。

补 3 个幂等断言：模型照抄场景、`_pin_risk_block` 连调两次、
`_ensure_risk_block` 连调两次。

### 举一反三
1. **写兜底逻辑时先问："被兜底的那一步成功时会怎样？"**
   只想"它失败了怎么办"，就会漏掉成功路径上的副作用。
   本例中"模型照做"恰恰是最常见的情况，却被当成异常来处理
2. **同一类兜底函数必须横向对齐幂等性**。一个幂等一个不幂等，
   意味着调用顺序会改变结果——而调用顺序往往由 LLM 流程决定，不可控
3. 这与 BC-17 同源：**实现了机制，但没验证机制在各种输入下的行为**。
   14 个集成测试覆盖了"模型丢弃评级"，却没覆盖"模型照抄评级"

## 🔴 BC-25：模型断线被评测装置算成了扫描器贡献

**严重度**：高（API 可用性差异会污染算法归因）
**发现于**：修复 BC-24 后首次联网冒烟

### 现象
模型 API 连接失败时，完整组仍可由确定性扫描器命中 INJ-01，于是被记为
`1/1`；关闭扫描器组没有兜底，被记为 `0/1`。表面上像扫描器贡献 100 个百分点，
实际上两组都没有得到任何模型判断。

### 根因
生产降级与消融评测混用了同一成功口径。生产上「LLM 挂了扫描器仍工作」是正确能力；
但算法消融要求两组共享「LLM 调用成功」这一前提，否则比较的是可用性而非检测能力。

- `degraded` 或 LLM 输出不可用的运行仍完整写入 JSONL，但 `ok=None`，不进指标分母
- 只要一轮中出现调用错误，命令非零退出，不允许拿部分结果写结论
- 生产降级能力继续由 `test_critic_gate.py` 单独验证
- 新增 `test_eval_harness.py` 两条装置级断言

### 举一反三
**实验装置也需要测试。** 业务 fallback、重试和降级在生产中是优点，
在因果实验中却可能成为混杂变量；两者必须分开计量。

## 🔴 BC-26：冲突扫描器一边误拦规范披露，一边漏掉同义改写

**严重度**：高（确定性门控的误报会稳定阻断正确报告）
**发现于**：v3 首次独立留出集

### 现象

HCLN-02 明确写出实缴资本存在“两种互不相容的记载”，并说明无法判断真实值、
不据任一口径评价资本实力。完整架构 A 组仍稳定 3/3 报
`conflict_silently_resolved`；关闭扫描器的 B 组没有这条稳定误报。

反方向上，HINJ-02 写“实际到位资本为1500万元”，再把工商 5000 万元解释为
过时口径。扫描器没有命中，原因是只认识“实缴资本”，不认识“到位资本”。

### 根因

规则的业务语义是“识别是否披露来源分歧”，实现却退化成有限字面词表：
“冲突/不一致”在白名单，“互不相容/不同口径/不同记载”不在；字段别名同样
只覆盖一种常见写法。确定性规则没有随机性，所以这类缺陷不是偶发误差，
而会每次稳定地错。

### 修复与断言

- `registration` 增加“到位资本”别名；
- 分歧披露标记增加“互不相容、不同口径、不同记载”；
- 正向断言：明确并列披露且拒绝选边必须零告警；
- 反向断言：用“到位资本”改写后单方面采信仍必须检出。

修后 `test_critic_gate.py` 21/21、确定性扫描器显式违规 7/7、开发集对照误报 0/18。

### 方法论处理

原留出集已被观察并用于修改词表，从此只能当回归集；即使修后在它上面变好，
也不能再称为独立泛化结果。封板需要新的未见盲测集。

## 🔴 BC-27：人工维护的词表必然有缺口——BC-26 修完仍能构造误报

**严重度**：低（误报，非漏检）
**发现于**：对 BC-26 修复的交叉复核

### 现象
BC-26 补齐了「互不相容 / 不同口径 / 不同记载」三类分歧披露表达并锁了回归，
留出集因此退役。但复核时仍能轻易构造出**正确披露却被误判**的句子：

```
"实缴资本在工商登记与财务附注之间存在分歧，需人工核实。"   → 误判 conflict_silently_resolved
"实缴资本5000万元与1500万元两个记载并存，暂不采信任一方。"  → 误判
```

### 根因
不是 BC-26 修错了，而是**修复方式本身有固有上限**：
`CONFLICT_DISCLOSURE_MARKERS` 是人工枚举的关键词表，
而自然中文表达"来源之间对不上"的说法是开放集合，穷举不可能完备。

每修一批词，就少一批误报；但总能再构造出下一批。这与
「扫描器负责机械判定」的定位并不矛盾——它换来的是零方差与零成本，
代价就是词法边界永远需要维护。

### 解决方案
补入「分歧 / 并存 / 两种」三词并加正向断言。

**刻意不收「存疑」**：该词属弱披露，可以与"但现已确认为 X"共存，
收进白名单会给单方面采信开口子。已加反向断言锁住这个判断：

```python
text = "实缴资本曾存疑，但结合财务资料现已确认为1500万元，据此评估资本实力。"
assert scan_report(...), "「存疑」+ 单方面采信必须被检出"
```

### 举一反三
1. **关键词白名单的每一次补充都应同时写正反两个断言**：
   补的词要放行，容易与之混淆的弱表达要仍能拦住。只写正向断言，
   等于把"这个词不该收"的判断留在了脑子里
2. **误报与漏检的取舍要显式写下来**。此处的取舍是：
   宁可让「存疑」类句子误报一次，也不给单边采信留口子——
   因为误报会被复核人看到，漏检不会
3. 更根本地：**若误报持续困扰，正确方向不是继续堆词，
   而是把"是否披露了分歧"交给语义判断**（LLM 那一层），
   扫描器只保留高确定性的模式。当前尚未到这一步，
   但词表每次扩充都应视为一次"该不该换手段"的提醒

## 🔴 BC-28：扫描器命中否定词片段，不理解否定作用域

**严重度**：高（稳定误报会由 critical 门控直接阻断正确报告）
**发现于**：v0.5 第二套独立盲测首次运行

### 现象

完整架构 A 组有 4/12 个 clean case 稳定 0/3，通过扫描器门控稳定误报：

- “不能据此认定为不存在”命中“不存在”；
- “数据范围没有覆盖”命中“没有”；
- “不能解释为没有股东”命中“没有”；
- “两套记录、无法相互校准、并列保留且不选边”仍未命中冲突披露白名单。

关闭扫描器的 B 组中，这四例的扫描器误报全部消失。

### 根因

扫描器以“字段别名与断言词是否在同一句共现”为主，不解析断言的语义作用域。
`不存在` 在“确认不存在”和“不能认定为不存在”中是相同子串；`没有` 在
“没有担保”和“没有覆盖担保数据”中也相同。继续补合规词只能处理见过的句型，
无法穷举自然语言中的否定、引用、条件和转折。

### 当前处理

本轮是封板执行任务，只记录、不修复。盲测集已退役为回归集。后续应重新界定：
确定性层只保留上下文无歧义的高精度模式；需要理解否定作用域或开放式分歧披露的
句子交给语义层。修复不得只再追加四个白名单短语。

## 🔴 BC-30：一致性校验把「合法增量证据」当成「状态漂移」

> 📌 编号更正：本条初次写入时误用了 BC-28（与「扫描器命中否定词片段」重号），
> 现更正为 BC-30。引用请以本编号为准。

**严重度**：高（会在接入真实数据源那天全面 fail-closed）
**发现于**：v0.5 交叉复核时的前瞻分析，v0.6 修复

### 现象（尚未在生产触发，属结构性缺陷）
`verified_profile_mismatches()` 的实现前提是：

> 清单里每一个 verified 字段，都必须能由初始 `company_profile` 重放出来。

当前成立，只因 Scout 至今**只追加 `attempted_sources`、从不翻转状态**。
一旦结构化适配器查到初始档案里没有的字段（如对外担保）并置为 verified，
初始档案自然重放不出来 → 被判为"清单与档案不一致" → `unratable` → **全面 fail-closed**。

即：**系统会把新查到的合法证据当成数据损坏**。而且失败方向是"越查越不可用"——
接入的数据源越多，评级越容易被拒。

### 根因
一致性校验只有**单一重放依据**（初始档案），却要校验**多来源**的核实结果。
校验逻辑隐含假设了"所有核实都来自同一处"，而这个假设正是接入适配器时要打破的。

更根本的是：`FieldCheck` 记录了"核实到了什么"，却没记录"**这条结论从哪来**"。
没有来源，就无法选择正确的重放依据。

### 解决方案（v0.6）
给每条 verified/conflicting 附加可审计溯源，并按来源分发重放依据：

| verification_origin | 重放依据 |
|---|---|
| `initial_profile` | 从 `company_profile` 重放（复用 `fill_field_checks`） |
| `structured_adapter` | 从 `evidence_store` 按 `evidence_ids` 回查并比对取值 |
| 缺失（旧检查点） | 显式降级记录 + 档案兜底重放，**不静默按档案来源处理** |

三条不可让步的规则，各有断言锁定：

1. **`attempted_sources` 不是证据**——只说明尝试过，与查到什么无关
2. **通用网页检索不是结构化核实来源**——自然语言无稳定字段映射，
   无法在重放时做等值比对；`VALID_ORIGINS` 是闭集，`web_search` 不在其中
3. **来源不明时不得静默猜测**——旧检查点走降级路径且必须出现在
   `report.degradations` 里，由 DataAnalyst 写进 `state["errors"]`

### 一个刻意的实现选择
`record_structured_evidence()` 作为唯一原子写入口，把「写证据」与「改字段状态」
绑在同一次调用里。分成两步就总会有人只做第一步——而"只改状态不写证据"
正是这套校验要拦的东西。

> ⚠️ 首版并没有做到这一点，只是把这句话写进了注释。见 [BC-34](#bc-34)。

### 举一反三
1. **校验逻辑的假设会随功能演进失效。** 「所有核实同源」在写下时是事实，
   在接入第二个数据源那天变成 bug。**凡是隐含"只有一种情况"的校验，
   都应先问：将来会不会有第二种？**
2. **失败方向要设计。** 本例的失败方向是"数据越全越不可用"，
   与系统目标完全相反。fail-closed 是对的，但**因为查到了更多证据而 fail**
   不是安全，是缺陷
3. **状态要带出处。** 只记"是什么"不记"从哪来"，任何多来源系统迟早
   会遇到无法校验、也无法解释的状态

## 🔴 BC-31：证据通过了校验，却没有进入评分数据 ⭐

**严重度**：最高（新增的负面证据被翻译成正面结论）
**发现于**：v0.6a 只读复核，同轮修复

### 现象
适配器写入「存在 1800 万元对外担保」，证据链校验 `ok=True`，
清单状态 `verified`。评分卡实际输出：

```
适配器证据：存在1800万元对外担保
verify_field_checks：通过
评分规则：未发现对外担保        ← relation 维度 0.0 分
```

一条新增的负面证据，被系统翻译成了**有利于放款的正面结论**。

### 定位过程
`risk_scorecard.score()` 有两份输入，来自两个不同的地方：

| 用途 | 数据来源 |
|---|---|
| 要不要评这一项 | `field_checks[i].status` |
| 扣多少分 | `company_profile` 里的结构化数据 |

适配器只写了前者。`_ok("guarantee")` 为真 → 进入打分分支 →
`company.get("guarantee")` 仍是空 → `未发现对外担保`。

### 根因
**这是 [BC-19](#bc-19) 的同形复发，只是入口换了。**
BC-19 是"档案没进 state"，BC-31 是"证据没进档案"。两次的共同形态：
*核实状态与取值来自不同数据源，而校验只覆盖了其中一条。*

v0.6a 建立的证据链校验只保证「清单 ↔ 证据」一致，
从没保证「证据 ↔ 评分卡读的那份数据」一致——**中间少了一层**。

### 解决方案
1. `verification.build_scoring_view()`：把结构化证据的 `profile_patch`
   合并进评分卡真正消费的那份数据，返回 `(view, unmergeable)`
2. `risk_scorecard.PROFILE_BACKED_FIELDS`：显式登记"风险分从档案取值计算"的字段。
   新增读档案的规则必须同步登记，否则会重新打开同一个洞
3. 证据无法合并（只有展示用 `value`、没有 `profile_patch`）→ **不予评级**，
   而不是拿旧档案算一个干净分数
4. 合并采用**追加**而非替换：追加最多重复计数（风险偏高），
   替换可能抹掉档案已有的负面记录（风险偏低）。授信场景只能偏高

顺带修掉同形的一处：`guarantee_circle` 此前无论查到什么都硬编码
`0.0 未发现担保圈涉入情况`，根本不读数据。它在 v0.6 图谱能力上线后
就会变成一模一样的缺陷。

### 举一反三
1. **"校验通过"和"结论正确"是两件事。** 校验只覆盖了它看得见的那一段链路；
   链路上任何一段没被覆盖，通过率就是虚的
2. **同一个 bug 会换个入口回来。** BC-19 修的是"档案没进 state"，
   于是我在"档案进了 state"之后就不再怀疑数据面。修一个缺陷时应当问：
   **这个形态还有哪些别的入口？**
3. **断言必须落在最终产出上。** 首版 22 条断言全绿，因为它们都停在
   `verify_field_checks().ok`。**中间报告为真，不代表最终决定为真**

## 🔴 BC-32：证据没有绑定字段、适配器、时间与冲突状态

**严重度**：高（校验可被绕过，含 `conflict_silently_resolved`）
**发现于**：v0.6a 只读复核，同轮修复

### 现象
`_replay_structured()` 首版只检查三件事：evidence_id 是否存在、
verified 时取值是否匹配、conflicting 时是否有 ≥2 条记录。
以下五种构造**全部通过校验**：

| 构造 | 首版结果 |
|---|---|
| 担保证据挂到关联方字段，只要取值相同 | ✅ 通过 |
| `source_adapter="web_search"` 走写入口 | ✅ 通过，且 origin 被盖成 `structured_adapter` |
| 删除证据本体的 `retrieved_at` | ✅ 通过 |
| 同字段并存 5000 万 / 1500 万，单方面标 verified | ✅ 通过 |
| 两条同源同值凑成 conflicting | ✅ 通过 |

第 4 条正是系统从 v0.3 起就在防的 `conflict_silently_resolved` ——
**只是这次发生在我自己写的证据层，而不是模型输出里**。

### 根因
两个独立错误叠加：

1. **只校验了"证据存在"，没校验"证据属于谁"。** evidence_id 是个指针，
   而指针指向的东西是否与当前字段有关，首版从没问过
2. **`source_adapter` 是调用方自由传入的字符串。** 我建了 `VALID_ORIGINS`
   闭集来挡 `web_search`，却又提供了一个把任意字符串直接升格为
   `structured_adapter` 的写入口——**闭集被我自己开的后门绕过了**

### 解决方案
- `_TRUSTED_ADAPTERS` 受信任适配器注册表，写入侧与重放侧**双向校验**
- 逐条比对 `evidence.field_id` / `source_adapter` / `retrieved_at` / `raw`
- `check.retrieved_at` 必须等于最新一条证据的时间
- verified 时若存在多个不同证据取值 → `conflict_silently_resolved`
- conflicting 需要 ≥2 个**不同来源**的 ≥2 个**不同取值**，
  且 `conflict_detail` 必须与证据一致
- 新增 7 条反向断言，每种绕过方式一条

### 举一反三
1. **闭集只在没有旁路时才是闭集。** 建了白名单，就要检查有没有别的门
   能把身份发出去。**枚举防线时要连同"谁能签发凭证"一起枚举**
2. **自己实现的规则和模型输出一样需要被怀疑。** `conflict_silently_resolved`
   一直被当成"模型可能犯的错"，结果它先出现在我的校验器里
3. **指针型引用必须双向校验。** 只验"目标存在"不验"目标是否属于我"，
   等价于没验

## 🔴 BC-33：来源降级只被披露，没有约束评级

**严重度**：高（来源不明的旧检查点可自动输出低风险）
**发现于**：v0.6a 只读复核，同轮修复

### 现象
构造一份全部 verified、但全部缺 `verification_origin` 的旧检查点：

```
degradations         : 20 条
replay_ok            : True
level                : 低风险
requires_human_review: False
gates_applied        : []
research_complete    : 不携带 errors/degradations
```

20 条"来源不明"一条都没有进入定级，终局事件里也看不到。
**等于用一行日志换一个可能错误的放款决定。**

### 根因（三层，缺一不可）
1. `allow_legacy_profile_replay=True` 是**函数签名里的默认值**，
   一个授信口径开关藏在了实现细节里
2. `degradations` 只写进 `state["errors"]`，而 `errors` 不参与任何判定
3. `build_complete_event()` 根本不带 `errors`

**这三层各自都"实现了"，合起来对结果零约束——[BC-17](#bc-17) 的原形。**

### 解决方案
- 默认改为**严格**：`POLICY.allow_legacy_profile_replay = False`，
  来源未迁移的检查点在决策路径直接 fail-closed
- 开关移入 `config/verification_policy.py`，统一配置可见、可切换
- 新增 `risk_scorecard.apply_provenance_gate()`：存在降级时
  **等级下限提升至中风险 + 强制人工复核 + 写入 gate**，与其它闸门同一机制
- 降级明细进 SSE 事件与 `research_complete`
- 兜底重放只留给显式迁移工具与非决策读取

### 举一反三
1. **默认值就是策略。** 大多数调用方不会传参，默认值决定了系统的真实口径。
   **安全相关的默认值不该由实现者顺手决定，要放进配置并写明理由**
2. **披露不是控制。** "记录下来了"容易让人觉得问题已处理。
   判断一个机制是否生效，只看**它能否改变最终结果**
3. **失败方向不对称时，默认必须倒向保守的一侧。** 误判为"不予评级"
   代价是一次人工复核；误判为"低风险"代价是本金

## 🔴 BC-34：「写证据与改状态绑定」只存在于注释里

**严重度**：中（宣称的不变式并不成立）
**发现于**：v0.6a 只读复核，同轮修复

### 现象
`record_structured_evidence()` 的文档写着"把改状态与写证据绑在同一个函数里，
这条路径在代码层走不通"。实际该函数**只写来源字段**，
不写 `status` / `value` / `conflict_detail`。测试因此长这样：

```python
guarantee["status"] = "verified"        # 调用方自己改
guarantee["value"] = "..."              # 调用方自己改
record_structured_evidence(...)         # 只补来源
```

两步依然是分开的，漂移窗口原样存在。

### 根因
我把**设计意图**当成了**已实现的属性**写进文档，并据此在交付说明里宣称
"那条路径在代码层走不通"。测试也没能证伪——因为测试自己就在手工改状态，
等于替被测对象把缺的那半件事做了。

### 解决方案
- 入口显式接收目标状态：`status=verified` 必须带 `value`，
  `status=conflicting` 必须带 ≥2 来源 ≥2 取值
- 一次调用写完 evidence_store 与 check 的全部七个字段
- 非法组合直接抛 `ValueError`
- 断言"调用前后状态确实变了"，且测试不得在调用前手工改任何状态字段

### 举一反三
1. **注释不是断言。** 描述性文字不会失败。**任何"这条路走不通"的说法，
   都要有一条走它并失败的测试**
2. **测试替被测对象补齐前提，就等于取消了这条测试。**
   与 [BC-15](#bc-15)、[BC-20](#bc-20) 同形：跑通了，但测的不是声称的那件事
3. **交付说明里的强断言要挑出来逐条验证。** 这句话是我主动写进汇报的
   "亮点"，恰恰因为是亮点才没有被自己怀疑

## 🔴 BC-35：用运行时间冒充证据取证时间

**严重度**：中（时效判断失真）
**发现于**：v0.6a 只读复核，同轮修复

### 现象
`fill_field_checks()` 用 `datetime.now()` 作为初始档案证据的 `retrieved_at`。
记录的是**程序读取档案的时刻**，不是证据真正获取的时间。
报告会显示"本次核查于今日完成"，而数据可能是三个月前抓的。

### 附带的一处自我修正
首版测试原本断言 `retrieved_at == checked_at`，失败后我把断言改成
"非空且以 20 开头"。当时的判断是"锁死具体值会让它变成时钟测试"——
这个判断本身没错，但**改完之后这条断言什么业务语义都不再校验**，
非法字符串也能通过。回避了时钟耦合，也回避了正确性。

### 解决方案
- 新增 `profile_retrieved_at()`：优先取档案自身声明的时间
  （`registration.retrieved_at` → 记录级 → `coverage.retrieved_at` 快照级）
- 取不到就**留空**，由重放校验记为降级，绝不生成当前时间
- 校验 ISO 格式；证据本体与清单副本的时间戳必须一致
- mock 档案补上 `coverage.retrieved_at`，让数据源声明自己的快照时间

修复过程中还暴露一个自身缺陷：时间解析只遍历"有档案载体的字段"，
`guarantee_circle` 这类靠推导得出的项整个缺席，反被误记为"取证时间不明"。
**与 [BC-21](#bc-21) 同形——从"已有数据"出发遍历，最缺数据的那一项反而漏掉。**

### 举一反三
1. **系统时间是最容易被误用的默认值。** 它永远可得、永远"看起来合理"，
   因此特别容易被拿来填一个语义完全不同的字段
2. **断言失败时，先问"是断言错了还是实现错了"，再问"改完还剩什么"。**
   把断言放宽到不再失败，和删掉它效果相同

# 第二部分：预判的 Bad Case ⚪

> **以下尚未发生**，是基于设计推演的风险点，用于指导迭代顺序。实际遇到后回填真实现象与解决过程；**预判错误的也要如实记录**——预判失败本身是有价值的信息。

## ⚪ BC-P1：模型给未核实字段填"合理"的值
**预期出现**：v0.2
**推测现象**：清单里"实际控制人"数据源无返回，模型根据股东结构自行推断一个人名并当作已核实填入。
**为何预判**：提示词层面的"请标注未核实"是软约束，而模型的训练目标偏向"给出有帮助的回答"，倾向于填空而非留白。
**预案**：升级为架构约束（v0.3）——状态机 + Writer 固定模板 + Critic 专项检测，让"填值"这条路在结构上走不通。

## ⚪ BC-P2：Critic 漏检隐含断言
**预期出现**：v0.3
**推测现象**：财务字段全部 `unverified`，报告未直接写数字，但出现"该企业经营稳健、偿债能力良好"——**隐含断言了未核实的财务状况**。显式断言好检测，隐含的难。
**预案**：Critic 提示词强调"评价性表述也算断言"；评测集专门构造这类用例。

## ⚪ BC-P3：数据缺失 → 判低风险
**预期出现**：v0.4 评测时被量化暴露
**推测现象**：司法数据源无返回 → 涉诉/被执行/失信三项无扣分 → 综合分低 → 输出"低风险，建议授信"。
**为何危险**："查不到"被当成"没问题"，是尽调系统最致命的失效模式。
**预案**：完整度闸门（v0.5）——司法维度缺项则等级至少中风险；总体核实率 <60% 判"数据不足，无法评级"。

## ⚪ BC-P4：便宜模型抽取准确率下降
**预期出现**：v0.7 模型路由
**推测现象**：字段抽取换便宜模型后成本大降，但结构化抽取准确率下滑。
**预案**：靠 v0.4 的评测量化取舍——"省 X% 成本、掉 Y% 准确率"，用数据决策而非感觉。

## ⚪ BC-P5：并行化触发 API 限流
**预期出现**：v0.7
**预案**：并发上限 + 退避重试；限流要计入 `errors` 而非静默吞掉（BC-02 的教训）。

## ⚪ BC-P6：恢复 LangGraph 后事件时序变化
**预期出现**：v0.6
**推测现象**：图执行的事件顺序与手写编排不完全一致，前端研究过程面板出现步骤错乱或重复。
**预案**：先固化一组 SSE 事件序列快照测试，改造前后对比。

# 复盘：这些 Bad Case 的共性

| 模式 | 涉及 | 教训 |
|---|---|---|
| **静默降级** | BC-02、BC-P5 | 把失败伪装成成功，比报错难查十倍。任何 fallback 都必须可观测 |
| **模型缺少必要上下文** | BC-03 | 模型没有时钟、不知道今天几号。要它做的判断需要什么基准，就必须显式给 |
| **跨产出无收口校验** | BC-01、BC-04、BC-19、BC-23 | 多来源/多 Agent 汇合处必须有一致性闸门，不能假设各方自洽。组件各自正确 ≠ 接起来正确 |
| **软约束当硬约束用** | BC-01、BC-22、BC-P1、BC-P2 | 提示词里的"请不要…"是建议不是保证。关键约束必须落到架构层 |
| **只检查已有结果** | BC-21 | 失败对象可能恰好没有产出，校验必须从预期全集出发 |
| **开关没有贯穿整条链路** | BC-15、BC-24 | 消融必须同时关闭执行、上下文注入、合并与过滤，并用行为断言证明 |
| **生产降级污染实验归因** | BC-25 | 失败调用要留痕但不进算法指标分母；可用性与准确性分开评测 |
| **依赖与取舍会过期** | BC-06、BC-07 | 当初"框架做不到"可能已随版本失效；无上界依赖等于赌运气 |
| **模型的副作用无边界** | BC-08 | 模型生成的代码在哪写文件、写什么名字，都必须由系统而非模型决定 |

**贯穿一切的一条**：在容错率低的业务场景里，**不能把正确性寄托于模型的自觉**。可靠性来自结构化约束、机器可判定的规则，以及独立的校验环节——这正是本项目的技术主线。
