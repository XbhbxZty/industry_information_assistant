# 匿名化真实案例：在「数据充分」条件下验证决策链

**日期**：2026-08-24
**结论先说**：这一轮抓到的东西比之前三十轮观察加起来还多，
其中一条是**一笔 2.5 亿元的错误授信建议**（BC-79）。

---

## 一、为什么要做

到 2026-08-24 为止，这套系统**从未在真实主体上产出过一次评级**。

十二个真实案例包全部落在「数据不足，无法评级」。看起来像是数据不够，
逐层查下去发现是**设计**：`company_profile.py` 对
`litigation` / `guarantee` / `registration` 这些字段要求由**权威数据源**
提供，而年报里那句「公司报告期未发生重大诉讼」是借款人的**自我披露**，
不算数——**而且不算数是对的**，授信要的是裁判文书网，不是借款人的说法。

于是：

- 评分权重、三口径额度测算、结论段、跨层判定在**有已核实字段**时的行为
- 一次都没有被走过

三十轮观察验的全是**拒绝路径**。产品真正要用的那条路径是空白。

## 二、怎么做的

### 2.1 为什么不给真实公司编造司法记录

案例包是真实上市公司的公开材料。要跑通就得补上语料里没有的
工商/司法/招投标数据，而那部分只能是编的。

**给真实、具名的上市公司编造司法记录，然后产出一份写着
「建议授信 X 万元」的报告，不能做。** 产出物本身看起来就是一份真报告。

解法是改名：编造的记录属于一个虚构主体，问题消失。
数值、结构、行文全部保留——比任何手写虚构语料都像真材料。

### 2.2 改名必须彻底，否则比不改更糟

只改主体名、留着关联方与人名，得到的是一个**看起来虚构、实际一眼可辨**
的公司，而它现在还挂着编造的司法记录。

`eval/anonymize_case.py` 的残留检查覆盖十个维度：

中文实体名、词根、股票代码（A+H）、统一社会信用代码、人名、
总部地名、拉丁串/拼音、邮箱、裸域名、完整 URL。

**其中六个维度是被独立复核推翻之后才补上的：**

| 轮次 | 漏了什么 | 为什么漏 |
|---|---|---|
| 1 | `3606`（H 股代码） | 替换表只写了 A 股 |
| 2 | `fuyaogroup.com` × 460 | 域名整个维度不在检查范围 |
| 3 | `灏月` `神农氏` `大地参业` | 只查表里列的**全称**，不查词根 |
| 4 | `福清` × 141 `普宁` × 504 | 没想到总部地名算标识 |
| 5 | `Kangmei` `KMYY` `kangmei@kangmei.com.cn` | 拉丁串与邮箱整个维度缺失 |
| 6 | `Talesun` `zhongli.com` `ZHEJIANG DINGLI` | 同上，另两个案例 |

**根因每次都一样：检查只能发现我已经列出来的东西。**
现在它自动派生词根、扫邮箱、扫裸域名、扫完整 URL，
能发现的东西多于我列出的。

同时带三张放行表（通用公司形式词、监管/媒体域名、按案例声明的行业词），
每张都写了理由——不放行的话每份语料报几十条假残留，
**检查变成恒亮的灯，真残留跟着被忽略**。

> 顺带记住：**误报和漏报是一对。** 六轮里两轮修误报、四轮补漏报。

### 2.3 URL 必须整体改写，不能只换域名

`money.finance.sina.com.cn/...?id=8152984` 里的 id 就是那份真实公告的
编号，只换域名等于没换。全部改写成
`https://archive.example/{case}/{sha1前12位}`——用哈希做后缀，
保证**不同来源仍然是不同 URL**；全换成同一个地址会让证据附录里的
来源互相塌缩，那等于伪造了「多个来源相互印证」。

### 2.4 主体确认率决定核实率上限

`_document_identity_zone` 读片段**头部 400 字**找主体别名，认不出就整片拒。
灌库前先自检，**在花嵌入的钱之前**：

```
case_11 康美   100%   ✅
case_05 苏宁    57%   ⚠️
case_03 福耀    10%   ⛔
```

拿原始语料做对照，确认 case_03 的 10% 是**它自身的性质**、与改名无关；
case_05 的 66%→57% 才是我改名造成的（把「苏宁易购」换成
「云铃智慧零售」，结构变了，别名断了）。

**教训：虚构名要镜像原结构，只换字号。**
`浙江鼎力机械股份有限公司` → `浙江骏昇机械股份有限公司`，
别名逐层剥后缀就能自然对上。

据此换掉两个案例，最终选：

| 案例 | 虚构主体 | 片数 | 主体确认 | 信用故事 |
|---|---|---:|---:|---|
| case_04 | 浙江骏昇机械股份有限公司 | 292 | 100% | 健康中型制造 |
| case_12 | 江苏泓瑞集团股份有限公司 | 280 | 100% | 连亏 + 违规担保 + 子公司重整 |
| case_11 | 晟康药业股份有限公司 | 828 | 100% | 证券虚假陈述 + 重整 + 非标意见 |

### 2.5 档案只转录已披露事实

案例包自带参考风险判断（`risk_level` / `recommended_action`）。
**那个不进输入**——照着目标等级去配档案，是拿答案倒推输入，
跑出来什么都不说明问题。它只用于事后对照。

`eval/build_anon_profiles.py` 里每一条都带 `_basis`，写明来自年报哪一处。
查不到的留空并写进 `not_queried_reason`——那才是诚实的信息缺口。

## 三、结果

### 3.1 核实率：33% → 93.3%

| | 宁德时代（无档案） | 三个匿名主体（有档案） |
|---|---:|---:|
| 必查项核实 | 5/15 = **33%** | 14/15 = **93.3%** |
| judicial | 0 | 1.0 |
| relation | 0 | 0.667 |
| opinion | 0 | 1.0 |
| 唯一未核实 | — | `guarantee_circle`（档案如实声明不覆盖） |

**「数据充分」这条路径第一次被走通。**

### 3.2 三条决策路径

| | 骏昇机械 | 泓瑞集团 | 晟康药业 |
|---|---|---|---|
| 综合分 | 9.0 | 24.5 | 31.0 |
| 营收法 | 155,978 | 81,026 | 83,050 |
| 现金流法 | **575,100** | **0** | **0** |
| 结论 | **可授信 10.9 亿** | **拒绝** | **拒绝** |

拒绝理由是**可核查的**：明确指出哪个口径、哪个数字、为什么不支持，
不是一句「风险过高」。

### 3.3 与参考答案对照

case_04 的参考判断（不是我写的）：

```yaml
risk_level: 中
recommended_action: 人工复核
credit_amount: null
```

系统产出：**中风险**、**强制人工复核** —— 等级与处置都对上。

参考答案的 `credit_amount: null` 表示「参考判断不给额度」，
与系统给出额度不构成矛盾——两者回答的不是同一个问题。

## 四、抓到的问题

### 4.1 BC-79：一笔 2.5 亿元的错误授信建议

`_latest` 取列表最后一项而非最近期间。详见 BADCASES BC-79。

**修复前**泓瑞集团（营收腰斩、连亏两年、四家子公司破产重整）
拿到「可授信 25,200 万元」，靠的是三年前那笔正现金流。
**修复后**正确拒绝。

### 4.2 我自己的输入错：档案取证时间晚于研究截止日

第一次跑，三个主体**全部 fail-closed**：每一个字段都被判
`post_cutoff_evidence`。

原因是我把 `RETRIEVED_AT` 写成一个三主体共用的常量（今天的日期），
而三个主体的研究截止日分别是 2025-06-30 / 2024-05-31 / 2022-05-31。

**闸门抓对了**——用今天的数据源快照去做一份截止到 2022 年的尽调，
本来就该拒。这也说明**档案不是一份静态资料，是带时点的证据**。

修复后加了写盘前自检：档案里任何晚于取证时间的记录会被当场拦下，
不用等流水线跑到 DataAnalyst 才发现。

## 四·五、追查「等级压缩」，又挖出 BC-80（2026-08-25）

顺着「评分能分辨、等级不能」查下去，逐层看维度分，发现泓瑞集团的
`relation = 0.0`、`judicial = 10.0`——**5.4 亿违规担保与四家子公司
破产重整一个字都没进评分**。

根因是档案与消费方之间没有契约校验，**同一个形状三个粒度**：
顶层键写 `guarantee_records`（消费方读 `guarantee`）、
`type: "破产重整"` 不在词表、记录子字段写 `counterparty`
（消费方裸下标读 `beneficiary`）。前两个静默输出「未发现」，
第三个直接崩溃。详见 BADCASES BC-80。

同时发现 BC-79 有第二个入口（`risk_scorecard.py:212` 同样的
`fins[-1]`），涉案金额占营收的比例按 2021 年营收算成 1.8%，
实际应为 4.6%。

### 修复后的三个主体

| 主体 | 综合分 | judicial | relation | 结论 |
|---|---|---|---|---|
| 骏昇 | 9.0 → **23.0** | 0.0 | **0 → 70** | 可授信 **1.70 亿**（原 10.9 亿） |
| 泓瑞 | 24.5 → **46.0** | 10 → 20 | **0 → 70** | 拒绝 |
| 晟康 | 31.0 → **26.5** | 10 → 20 | 0（确无担保） | 拒绝 |

骏昇的额度从 10.9 亿降到 1.70 亿——9.22 亿担保作为或有负债被扣减。
泓瑞从「低风险区间」（≤25）爬到 46.0。

**这两轮修复都不是靠测试发现的，是靠「一份按另一套习惯写的档案」。**

## 五、待查：评分能分辨，等级不能

```
修复前：骏昇 9.0  ｜ 泓瑞 24.5 ｜ 晟康 31.0   → 全部「中风险」
修复后：骏昇 23.0 ｜ 泓瑞 46.0 ｜ 晟康 26.5   → 仍然全部「中风险」
```

阈值是 `≤25 低 / ≤50 中 / ≤75 高`。

**修复前**：骏昇与泓瑞的分数都落在「低风险」区间，是那条日期闸门
把下限抬到中风险的——**中风险是闸门给的，不是评分给的**。

**修复后**：三个分数都真的落在中风险区间（25–50），泓瑞的 46.0
已接近上界。评分确实在往对的方向走。

于是问题变得更清楚了：**一家连亏两年、营收腰斩、违规担保、
四家子公司破产重整的企业，46 分（中风险）合不合理？**

这已经不是缺陷，是**评分口径的问题**：

- `破产重整` 现在归到 `涉诉` 类，但重整的严重性显然高于普通诉讼
- 「违规」担保与普通对外担保同分（都是 70），而前者是合规问题
- 「否定意见内部控制审计报告」没有对应的评分项

要不要给这几类信号独立的类型与更高的权重，是业务口径决策，
不是代码缺陷。**在业务方定口径之前不改。**

## 六、这一轮验证了哪条老纪律

**「自己写的测试只能验证自己想到的失效模式」。**

BC-79 藏了这么久，是因为两个 mock 档案**碰巧**按「最老在前」排列，
而测试是我写的、档案是我排的、三十轮观察用的也是它们——**闭环**。

一份按行业惯例（最新在前）排列的真实档案，**第一次接触就打破了闭环**。

复盘那一节里那句话在这里第三次应验：

> 要打破闭环，只有引入一个不是我写的另一半。
