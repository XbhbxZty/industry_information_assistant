Chapter 10 / 把执行变成可读界面

10　后端执行如何出现在界面上

后端运行状态、网络事件和 React 页面状态是三个对象。后端可能已保存结果但客户端没有收到最后一条事件；页面也可能展示了报告草稿但研究仍在等待复核。理解这些差别，才能判断“卡住”“断开”“完成”分别意味着什么。

10.1 从图事件到卡片的六个子过程

  1. 图执行产生事件字典：例如阶段说明、清单更新、报告草稿、人工复核请求。它是结构化消息，不等于逐 token 输出。
  2. 服务序列化：_format_sse 把字典转成 JSON，写成 data: {...}\n\n。服务结束时另发 [DONE] 标记。
  3. 路由返回持续响应：StreamingResponse 提供 text/event-stream；前端 API 用 fetch adapter 和 responseType: stream，拿到字节流而非一次性 JSON。
  4. 增量解码与缓存：TextDecoder 使用 stream 模式处理 UTF-8，避免一个中文字被跨网络包拆开后直接乱码；buffer 保留尚未完整成帧的内容。
  5. 按当前协议分帧：用两个换行拆帧，取 data: 行，跳过空内容与 [DONE]，JSON.parse 后交给 handleEvent。
  6. 按事件更新状态：只取尽调决策相关内容，用局部 patch 或保留旧值的合并方式更新 DDState，再由页面组件展示。
网络包 1：data: {"type":"phase","content":"正在
网络包 2：核查"}\n\ndata: [DONE]\n\n

拼接完整事件后：stage = "正在核查"
[DONE]：仅跳过，不把 phase 改成 completed

上例为分包示意，\n 表示协议换行，不是本页真的打开网络流。当前解析器针对本后端的单行 JSON、LF 双换行格式；没有实现所有 SSE 语法。它忽略单条 JSON 解析失败，且流尾无双换行的残片不会被当成完整事件消费。不要把它描述成通用 SSE 客户端。

10.3 页面状态机与后端持久化状态不是一张表

idle → running新任务清空旧展示，生成会话 ID，发起请求。running → awaiting_review后端暂停；已经可以展示待签报告。running → completed / error根据明确事件或断流检查收口。

DDState 还含 report、risk、investigation、errors 和 profileRef。调查层有独立展示区，不能混入规则评级卡片；告警不能在最终事件到达时被整体覆盖消失。页面把清单和核实率放在一侧，把风险、调查、报告放在另一侧，这是数据责任分层的界面表达。

为什么 profile_ref 要特殊处理？

它是“这次研究采用哪份档案”的公开引用。前端要求非空 ID、正的安全整数修订号、64 位小写十六进制内容摘要和准确的来源标识。某条事件没有带引用时保留旧值，不能清空；开始新任务或 reset 才清空。这个形状检查并不等于浏览器验证了服务端 HMAC。

10.4 哪些恢复能力已存在，哪些不能默认有

  1. start 等待流结束后，如果 phase 仍为 running，会标为 error，并提示未产出结论；[DONE] 不是完成依据。
  2. 旧任务的 AbortController 会在新 start/reset 时被终止；这取消的是客户端读取。不能据此宣称后端持久化工作已全部撤销。
  3. Hook 定义 cancelled 以接收服务事件，但当前尽调专页没有因此自动提供完整的“取消、历史列表、刷新自动恢复”操作。
  4. 当前专页状态主要存在 React 内存中。后端有检查点接口，并不代表该页面刷新后一定自动回填旧任务；应沿实际调用核对。
  5. 专用复核工作台有自己的材料读取和决定重试逻辑，不要拿尽调页 Hook 中较简单的 review 处理，概括所有复核流程。
看见断流先分清“服务没完成”还是“完成结果没传到你这里”。正式复核重试需保留原决定；不能把重新创建研究、用新决定覆盖和恢复原决定混为一谈。对应后端边界见第 09 章。

start 的终态检查与 reset · HTTP 错误流解码

本章自检：报告已显示、HTTP 200、最后收到 [DONE]，三者是否足以证明完成？

不够。报告可能是草稿，HTTP 200 只是流已建立，[DONE] 只是服务结束标记。要结合明确的业务完成事件；复核还要对应服务器持久化终局。不能只以“页面没再转圈”判断业务完成。

11.2 先确认同一个目标库，再谈升级

resolve_database_urls 是数据库目标的共同解析入口。DATABASE_URL 只要出现就优先，不是“无效了再悄悄试 POSTGRES_*”。组件式配置仍被支持；用户名和口令中的特殊字符需要正确编码。SQLAlchemy 与 psycopg 使用不同驱动形式，但应指向同一逻辑库。

  1. 确认进程配置选择的主机、端口、数据库和用户名；不要把完整口令 URL 粘到公开日志或文档。
  2. 区分应用、迁移命令、检查脚本的加载位置。应用和部分脚本会加载环境文件，纯 URL 解析器自身不会替你加载它；不同启动目录/进程变量可能导致目标不同。
  3. 确认目标是独立测试库还是已有业务库。后者需要备份、停写窗口和明确变更授权，不能拿单测习惯直接初始化。
  4. 检查 Alembic 版本与实际结构；“有数据库”不是“已处于当前 schema”。

11.3 空库、旧库、已管理库走不同路线

现状应理解的动作不能做的替代
确认过的独立空库按迁移链升级到当前 head，之后再启动应用用 ORM create_all 冒充已经执行全部迁移
无版本号的已有库先只读结构预检；符合已知精确基线后，按受控准入流程处理直接 stamp head，让版本号掩盖缺表/缺触发器

11.4 密钥配置不是只填一个 JWT Secret

管理员档案审计和研究检查点有不同密钥环。active ID 决定新签发，保留的旧 key 用于验证历史。改 active 不等于旧签名自动换 key，更不代表旧 key 可以删掉。

  1. 档案审计使用 COMPANY_PROFILE_AUDIT_KEYS_JSON 与 COMPANY_PROFILE_AUDIT_ACTIVE_KEY_ID；不要与其他用途随意复用。
  2. 检查点显式密钥环使用 RESEARCH_CHECKPOINT_KEYS_JSON / RESEARCH_CHECKPOINT_ACTIVE_KEY_ID，旧 v2 快照另有 legacy key 指定。只有新设置完全未出现时才保留文档所述的旧单密钥兼容模式。
  3. 签发切换前保留旧验证材料，核对 alias、key ID 与格式；不能把摘要或 MAC 当作原始密钥。
  4. 退役前使用只读引用和验签预检。当前库通过不等于其他库、备份、进程和正在运行任务都没有旧引用。
  5. 丢失历史密钥时停止把历史当作已验证状态；重新算 SHA 或随手补签并不能恢复原本的可信依据。

预检工具若发现 LangGraph 历史表仍有数据，会保守阻断检查点 key 退役，而非猜测只看最新业务行已经足够。工具不会自动删 key 或更新用户配置。

11.5 用最小链路确认能运行，而不是一次全开

  1. 先确认代码版本、依赖与目标配置，不把旧文档中某台机器的绝对 Python 路径当成通用要求。
  2. 处理 schema 前提，再启动 API。后端入口为 backend/app/app_main.py，不是凭经验猜的 main.py；前端 dev 脚本为 Vite。
  3. 确认登录与只读列表，再测稀疏档案创建和权限拒绝；只有明确允许写独立测试环境时才执行。
  4. 观察图检查点是否实际使用 PostgresSaver。当前工厂在异常时仍可降级 MemorySaver 并告警，服务“能运行”不保证跨进程恢复成立。
  5. 最后逐项加入本地文档、模型与独立复核，分别记录输入与输出，不以单次页面打开作完整验收。
Git 回退只改变代码。已迁移的数据库、新格式快照、签名密钥和文档索引不会随之回退。真正回退必须核对匹配的数据备份与密钥；本手册不建议用旧代码直接读取新格式状态。

Chapter 12 / 用证据继续开发

12　怎样验证、排查和继续开发

一个功能至少有三个问题要回答：代码表达了什么、指定输入下行为是否正确、真实材料和真实模型下效果怎样。源代码审阅、自动化测试和模型评测分别提供不同证据，不能互相代替。

12.1 每一层测试能证明什么

层级主要观察对象不能顺带声称
纯逻辑／单元清单、来源覆盖、规则、签名内容、异常判据实际数据库事务和页面按钮正确
API 合同真实路由参数、依赖、角色和错误映射替换的依赖已代表线上服务
真实 PostgreSQL事务、锁竞争、触发器、版本与领取原子性跨进程重启和网络断流已测
独立进程 HTTP实际启动、JWT、真实路由、杀进程后恢复浏览器渲染、真实 LLM 与外部搜索质量
前端行为／构建／类型响应拦截、纯逻辑、打包和静态类型构建通过等于 tsc 通过，或布局可用
浏览器交互输入、按钮、页面状态、可访问性与视觉数据库所有并发边界和模型事实准确率

12.2 先给系统题目，再让评测器看答案

仿真输入描述企业、申请、资料与已知可用来源；oracle 是评测方保留的预期判断和依据。生产案例 loader 不能导入评测答案模块。否则模型只是看见答案后复述，漂亮的命中率不能证明系统会尽调。

  1. 准备正常、矛盾、风险、资料不足等案例，并固定主体、时间、资料内容与版本。
  2. 生产路径只接收 input；保留实际执行得到的检索、核验、报告和错误，不把 oracle 塞进上下文。
  3. 评测器单独装载 oracle，并核对 case_id、claim_id、来源引用和金额单位等是否与案例对应。
  4. 比较核实、矛盾、部分支持、未核实等结果；别只看最终报告有没有出现某个关键词。
  5. 将 API 不可用、解析失败和真正的错误判断分开统计。全部调用失败应是 ERROR，而不是 0% 或某组件“有效拦截”。
为什么还需要测试评测器本身？

现有 test_eval_harness 用故意断线的 Critic 检查：模型调用失败时 ok 必须为 None，不能算进成功／失败率分母，更不能被归功于确定性扫描器。另测 holdout 与开发集 ID 不重叠。它证明的是评测计数纪律，不是模型本次实际表现。

12.4 一个异常，按哪条路径倒查

  1. 固定复现身份：代码提交、接口、会话 ID、用户角色、档案 revision、截止日、搜索模式；不记录 token 或整份私有材料。
  2. 找最早偏离预期的边界：请求没到后端、后端拒绝、检索没结果、候选被拒、证据重放失败、评分与报告不一致、还是完成结果没送达？
  3. 分清未知与失败：unverified 本身不是 bug；如果原因是服务不可用，记录失败原因，不能伪造无记录让测试过。
  4. 审查测试夹具：模拟来源是否覆盖了所有派生字段？替换的 Depends 是否是路由真正捕获的对象？进程到底用 PG saver 还是内存替身？
  5. 做最小修正：先写能暴露问题的断言，再修正确层。不要通过降低安全校验或改 oracle 让失败消失。
  6. 验证同层与相邻层：例如改 API 响应约定要测 HTTP 错误和前端拦截器；改复核最终提交要测断流、原决定重试和并发。
真实 Bad Case 不是只写“修好了”。至少保存：复现条件、观察到的错误、根因、影响、修正、回归断言、实际结果、提交和遗留限制。对于只读审阅发现，应写“源码审阅发现”，不能虚构曾发生的线上事故。

12.5 示例：新增一个字段为什么不只改表单

假设要新增一种交易核查字段，先确认它究竟是企业属性、事件、交易级明细还是探索性线索。不能直接把一个文本框值当成可评分字段。下面是按责任检查的路线，不是要求每次都改全部文件。

检查层必须问清的问题
业务与固定清单field_id、场景、是否必查、空结果是否有意义、单位和主体范围是什么？
录入与数据源从管理员字段、Adapter 还是文本候选获取？哪些来源才可支持它？
提取与验证数值、日期、原文、statement_scope、冲突怎样处理？
消费与评分只用于叙述、用于闸门，还是进入额度计算？缺失是否应阻断？
持久化／恢复是否新增需要封签和重放的内容？旧状态兼容或拒绝策略是什么？
报告与界面字段、解释、来源、错误以及人工覆核怎样显示？
测试与记录正常、缺失、冲突、越时点、错误主体、重复决定等哪些反例受影响？

相反，如果只是改展示标签，可能完全不需要迁移数据库或改模型提示词。先明确责任边界，再决定变更范围，符合本项目“先实现、保留关键正确性、避免无关重构”的节奏。

12.6 这份手册怎样保持可追踪

正文按章节拆成维护片段，最终仍生成一个离线 HTML。源代码片段从固定提交读取，保留原行号和文件摘要；代码变化不会静默改变旧解释。所有章节与词条通过内部锚点互相跳转。

node docs/project-handbook/build.mjs
node docs/project-handbook/verify.mjs

这两个命令只构建／检查文档，不会启动 API、连接数据库或调用模型。修改引用后必须保证锚点唯一；检查内容包括链接、章节存在、脚本逻辑、源码一致性等。它不是全功能浏览器验收，不能据此宣称任何屏幕尺寸排版都已确认。

继续开发时先查看 Git 状态和最近提交，保留未提交成果；小阶段完成后记录真实检查结果与 Bad Case，再保存检查点。下次从检查点接续，不重新实现已完成且验证正确的功能。

本章自检：改了测试夹具后通过，是否代表业务代码曾存在相同 bug？

不一定。比如错误的来源字段或重复开启 HTTP client 会让验收先在夹具中失败。必须区分测试设施问题、实现问题和文档误述；记录真实发生在哪一层，不夸大为线上故障。
