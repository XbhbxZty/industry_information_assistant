04 / 数据入口

多种数据入口如何共存：先问“它能证明什么”

尽调不是把所有看起来像企业信息的东西拼成一份“更全的档案”。同一个名称可能来自演示用的 companies.json、管理员维护的档案、受控的结构化数据源、离线案例包，或者一段待检索材料；它们的授权范围、可复现程度和可以改变的下游状态并不相同。本章的工作目标是建立一张入口地图：先分清数据从何处进入，再判断它可否把某个 field_check 变成 verified，最后才谈评分或报告。

先给结论。静态企业档案与当前管理员档案是“初始 profile”路径；mock Adapter 是受注册表约束、可重放的结构化补充路径；案例包是评测/离线材料路径，oracle 更是评测器自己的隐藏答案。它们不能因为都含有公司名就相互替代。尤其不能把 Adapter 的空返回、案例 oracle 或管理员的自由文本解释成已核实的外部事实。

这张表故意把“存在哪里”和“业务上是什么”分开。举例说，静态 JSON 与 mock JSON 都是文件，但前者是初始档案，后者由 Adapter 拿到后还要回答覆盖范围、查询时点、原始返回和字段投影；案例材料也可能是文本，但其可检索性被 case/session/主体的绑定限制。阅读下游代码时，应该沿着 选择键 → 状态变化 → 可重放证据 追踪，而不是只搜索某个字段名。

静态 companies.json：教学/默认档案，不是兜底真相

旧的静态档案加载器把文件路径固定在应用数据目录，list_companies() 逐条调用 profile schema 校验。它不是“读不出来就照样给一个空公司”：未知键、非法词表或不合规结构会使该条被拒绝加载，避免消费者把一个未能识别的字段静默忽略，再把 coverage.queried 误读成“查过且没有”。加载失败时整个原始读取会退回 {"companies": []}，这表达的是没有可用的静态条目，绝不支持把它翻译成“该企业无风险”。

静态 profile 的典型输出是 name、registration、financials、coverage 等结构，随后由图初始化 facts 和固定清单。这里的空值有严格业务含义：字段根本未出现在 profile、字段存在但值为空、以及 coverage.queried 明确说某项已查询而无记录，不能混成一个空字符串。第三种才可能在某些“事件型”清单项中支撑“经查询无记录”；前两种仍是信息缺口或数据异常。

小例子：为什么空数组不能自动降低风险

若一个静态 profile 根本没有 guarantee，并且 coverage 也未声明查询过担保，它只意味着此档案没有担保信息。若 Adapter 成功查询了担保项，原始返回为 guarantee: []，且该字段是“无记录有业务意义”的事件型项，才可由 Adapter 记录一条“经查询，无相关记录”的结构化结论。若信用代码缺失导致 Adapter 找不到主体，则连第二步都没有发生。后两种输出都可能显示为空列表，业务结论却完全不同。

Adapter 的子过程：登记、查询、抽取、投影、写证据

  1. 声明能力并登记。子类必须声明非空 adapter_id、description、covers，实现 fetch、extract 和必要的 project_profile_patch。实例注册时进入 _TRUSTED_ADAPTERS；只有这个注册表内且具确定性投影器的来源才能获得 structured_adapter 身份。
  2. 先找主体，再返回查询覆盖。fetch(company) 用信用代码等键找数据。没有主体时返回 None，而不是伪造 queried=[]；找到主体才构造 AdapterResult(queried, raw, retrieved_at, not_queried_reason)。
  3. 只处理尚未落定且本 Adapter 覆盖的字段。基类跳过 verified、conflicting、not_applicable。运行顺序不是“后面的更可信”；替换已有结论需要明确的替代证据语义，不能靠后执行覆盖。
  4. 把原始返回和清单状态原子地绑定。抽取到的值、查询时点与 raw 进入 record_structured_evidence。该入口会检查注册身份、时间格式、字段投影和证据替代关系；输出的是 evidence id，并把当前结论绑定到对应 field_check。
声明/注册可重放的结构化来源主体匹配None 与已查询分开逐字段应用只补未落定字段证据写入raw、时点、投影、状态绑定

这个顺序的业务意义是：报告里“已核实”不应该只是一句模型文字，而要能从字段结论回到适配器 ID、原始结构化返回、检索时间和确定性 profile patch。另一方面，注册不是安全魔法。把一个无法等值重放的网页/模型结果注册进去只会把不稳定文本伪装成结构化事实，所以通用网页检索和 LLM 抽取被明确排除在此边界之外。

查询状态表：不要把 [] 读成同一个意思

代码信号清单应保持/变为报告可说什么反例推演（非本轮事故）
fetch() is None不改字段；结果说明 adapter_no_subject“该结构化源未定位到主体”，需要主体核实把它写成“无担保”会把匹配失败洗成正面结论。

这里的“事件型/属性型”不是数据结构的漂亮分类，而是风险语义。担保、处罚、诉讼常常存在“正式查询无记录”这一信息；统一社会信用代码、企业名称等主体属性的缺失却意味着主体归属或数据质量问题。每增加一个清单项，都要先定义其无记录语义、覆盖责任和失败文案，不能只给前端新增一个空字段。

mock 的位置：用于受控演示与回归，不是假装连了外部库

当前启用列表把 RelationRegistryAdapter 与 GuaranteeCircleAdapter 实例化并注册；前者从项目内 data/sources/relation_registry.json 缓存读取，按信用代码取一条记录，覆盖关联方、对外投资、担保。它的 raw 仍会随结构化证据保存，从而测试可验证“某个字段为何变成 verified”。但是文件注释已经说明这是 mock；不要在手册、接口文案或报告里写成已接入工商、法院或担保公司的真实 API。

注册列表还表达了另一个常被误会的点：Adapter 的数组顺序主要为运行记录的可读性，不是证据优先级。基类在字段已经落定时跳过，因此先后执行并不能获得覆盖权。要真正接入一个生产数据商，除了添加类和列表，还必须定义授权、主体键、覆盖字段、空记录意义、原始响应保留周期、可确定性重放的 patch、失败分类，以及对应的集成测试；付费 Key 的存在本身不等于已完成这些工作。

案例包与 oracle：同包相邻，不等于同一条数据流

仿真案例的生产输入由案例加载器解析；评测器随后才能加载同目录的 oracle/expected.json。oracle loader 会要求根目录和 oracle/ 都是包内真实目录、拒绝软链接逃逸，并校验 schema 版本、case id、claim id 与 source id 必须和传入的生产案例精确对应。这防止“拿 A 案的标准答案评 B 案”或用目录穿越换答案。

隔离更重要的目的不是文件安全，而是避免评测污染。Agent 应该只看题目、授权材料和正常检索结果；oracle 是评测器用来判断 Agent 输出是否符合预期的隐藏标准。若把 oracle 读进工作流状态，即使答案正确也无法说明模型或规则从材料得出结论。反过来，案例包离线 RAG 只是一个尚未接入 V2 主研究图的组件契约，不能被描述为“管理员上传材料已经自动接入了 RAG”；二者选择的主体、输入对象和生命周期不同，详见第 05 章。

自检：案例负载失败时可否偷偷换一个 oracle？

不可以。oracle 必须针对已经成功加载的明确生产案例校验；生产 case 缺失、UTF-8/JSON/schema 非法、claim/source 集合不一致，都应使该评测失败。换另一套“看起来接近”的 expected.json 会掩盖测试夹具或加载器问题，也会使分数失去解释性。

管理员路径与静态路径的区别：明确 ID 优先，损坏时失败关闭

管理员保存的是可审计的企业档案；启动研究时，显式提供的管理员 snapshot 和其 ref 必须同时存在并通过校验。图加载器会先采用它，且拒绝在 snapshot 缺半边时退回到名称匹配或 companies.json。这样做避免“档案 ID 失效后悄悄研究同名静态公司”这一串案风险。没有明确管理员档案时，才会使用静态匹配或为外部资料尽调构造只含主体名的动态 profile；动态 profile 不伪造工商、财务或担保字段。

因此管理员编辑入口不等同于 Adapter：前者可以携带字段级来源和版本冻结，后者必须输出结构化 raw、受注册表约束、按清单补值。管理员 materials 是另一个更窄的边界：当前认证用户可以调用同一档案内的无分数词法检索，并明确标 eligible_for_structured_evidence: false；它不是现成的组织 RAG。第 05 章会把三类材料的实际接线拆开。

05 / 材料与 RAG

材料命中不是事实：从上传到证据要跨过几道门

“RAG 已接入”是最容易造成误解的一句话。本项目里至少并存三类机制：用户个人知识库的上传、解析、切块、向量化和 Milvus 检索；离线尽调案例材料的确定性内存检索；管理员企业档案内 materials 的档案内词法搜索。它们都可能返回文字，但只有少数、经过来源/主体/日期/原文和字段规则验证的候选，才可能影响尽调清单。检索相关性、模型抽取和字段核验必须分开读。

当前边界。个人知识库链路已经有上传与后台处理实现；研究启动时的本地检索范围从关系库按用户授权解析。管理员档案材料目前并未被接入个人 KB、向量化或证据桥，而是单档案、无分数的关键词检索，且结构化证据资格固定为 false。未来组织级材料库不是当前已接通路径，不能提前写成产品能力。

先分三类材料，才不会把“可搜索”误读为“可评分”

材料系统当前输入/存放当前召回进入结构化证据的情况
个人知识库认证用户在自己的 KB 上传文档；文档行有 pending/processing/completed/failed 等状态，切片写 MilvusScout 在已解析的授权 KB scope 中做本地向量检索命中先是检索结果/事实候选；尽调模式仍需经过证据桥的确定性闸门。
离线案例材料已经由生产案例 loader 实体化的授权材料，按 session/case/subject/cutoff 建内存 corpus组件自身的确定性词元排序，结果附 chunk 身份和摘要哈希当前只有组件定义与测试调用，未接 V2 主研究、Scout 或证据桥；结果也不属于普通个人 KB 形状。
管理员档案 materials管理员档案行的补充文本/标题/引用认证用户可在同一 profile 内以词元子串全命中检索，返回无分数列表当前硬编码 eligible_for_structured_evidence: false；不自动拷入研究快照或向量库。

这一区分解决一个实际业务问题：企业提交的一份 PDF 可以是有用线索，也可能是未审计自报；离线评测材料可能是限定语料；管理员的备注可能只是运营补充。若不保留来源和授权范围，系统可能把 A 用户的文档给 B 用户召回，或把一条过期自报直接变成“已核实财务数据”。

源码：个人 KB 上传与后台处理 · 生产案例材料解析 · 离线案例语料构建 · 档案材料搜索权限与边界

个人知识库上传链路：先有文档状态，后有可检索切片

  1. 认证与落库。上传接口先把 URL 中的 kb_id 解析为 UUID，并以 KnowledgeBase.id == kb_uuid 且 user_id == current_user.id 查找。文件类型通过白名单后暂存，创建 Document 行，初始 status="pending"，再把后台任务排入队列。
  2. 后台解析与状态收敛。后台任务重新读 Document，将状态设为 processing，调用 DocMind。成功后写 completed、chunk_count 并清空错误；解析、嵌入或插入失败则写 failed 和 error_message。无论成功失败都会关闭会话并删除临时文件。
  3. 文本切块。chunk_text 默认每块 500 字符、重叠 50，优先在中文句号、问号、英文句号或换行的后半段边界截断。空文本得到空切片，后续处理必须以“文档内容为空/切分失败”收束，不应标 completed。
  4. 嵌入与索引。每个 chunk 生成 embedding；空返回或嵌入数与切片数不一致都失败。成功时为每段写入 id=<document_uuid>_<index>、doc_id、kb_id、filename、content、chunk_index 和 vector，并插入由 KB UUID 导出的 Milvus collection。

注意 HTTP 上传成功只表示“已创建待处理任务”，不是“内容已经可召回”。页面或调用方若在 pending/processing 期间读取切片，应按文档状态获得尚未完成的回应；不能因为 document_count 已加一就假定 Milvus 已有向量。反过来，处理失败也不等于“文档没有相关信息”：失败原因可能是解析超时、空文本、向量服务返回空、向量数量不匹配或数据库/Milvus 异常，应保留为可恢复的操作失败。

已完成也不是读取成功的强保证。切片查看接口在确认 doc.status == "completed" 后才访问 Milvus，但捕获任意 Milvus 异常并返回 chunk_count: 0, chunks: []。因此这个响应形状目前无法区分“该 completed 文档确实没有切片”和“向量读取失败”；它是当前接口限制，不能拿空数组断言文档没有可检索内容。

源码：上传、后台状态与临时文件清理 · 切块、embedding、UUID 身份与插入 · completed 后的切片读取与空结果降级

检索授权：Milvus 不知道“谁能看”，范围先在关系库裁决

向量记录有 kb_id，但 Milvus schema 本身没有 user_id；因此 Scout 不应凭调用方传来的 collection 名自己决定能搜什么。resolve_kb_scope(db, user_id, kb_name) 从 PostgreSQL 的 KnowledgeBase.user_id 找当前用户可用的 KB，生成 collection、KB UUID、名称和 document_count 的可序列化范围。集合名由 UUID 单点生成，而不是 KB 名称：名称仅在单用户内唯一、可改名、删除后可复用，曾造成同名库互相覆盖/复活的风险。

KbScope 本身要求空范围带 failure_reason，但当前研究路由只记录这段详细原因到日志，随后调用 scope.as_state()，把空列表传给 Scout；这个序列化字段不带 failure_reason。因此端到端不会保留“无用户身份/指定 KB 不存在/数据库异常”的细分原因，Scout 只能按空 scope 形成通用本地检索失败。另一方面，某已授权 KB 的 document_count > 0 但 collection 不存在，Scout 的本地检索可识别为索引缺失；只有 document_count 为 0 才可能是本来没有材料。两者都不应被写成“已搜索且没命中”。

反例推演，不是本轮事故记录。若系统按可变的 KB 名称而非 UUID 拼 collection，用户 A 与 B 各建“财报”时可能落入同一 collection；即便内容很相关，也会造成授权越界。相关性评分不能修复主体或权限错误。

源码：路由记录原因后仅传 scope entries。这里的“下游仅能处理空 scope”是对该序列化边界的代码推论，不把日志中的详细原因描述成已端到端传递的字段。

Scout：召回先进入候选视野，不直接翻转清单

Scout 对每个研究章节组织 web/local 查询，收集成功结果，并区分 SearchOutcome.ok 与失败原因。它不会仅用一个空数组表示 HTTP/索引/超时故障和“确实 0 条命中”；失败会写入研究 state 与事件，成功的 local 检索结果才加入本节的 all_results。模型基于受限窗口提出 extracted facts 和 field_evidence 候选；窗口上限也会记录被丢弃数量，避免“材料根本没给模型看”被伪装为模型判断失败。

在尽调模式中，普通模型抽出的事实首先仍是未核实事实；桥接器随后检查其所指向的结果是否属于授权范围、主体是否相符、发布日期/截止日是否合格、字段是否在固定清单、所声称的值和期间能否在连续原文窗口中定位、金额单位和报表口径是否足够。模型自己给出的 exact_quote 会被忽略，由系统从原文重新切出 quote。换句话说，模型的职责是提出“看哪一段、像哪个字段”，不是为自己的文字签发证据。

1. 收集而非信任

collect_analysis_evidence 只接受固定清单字段的候选，并重建引用窗口。候选缺值、字段未知、来源不在本次结果、主体不匹配、找不到连续原文或字段关键词、财务缺少期间/数值/单位等，都会进入 rag_evidence_rejections；它们应在摘要中被计数，而不是从状态里消失。

2. 完整度与冲突也是结论

一段提到“营收”的原文并不覆盖近三期财务；一行股东姓名不代表完整股权结构。桥接器按字段定义检查完整度。若已有管理员 profile 或结构化 Adapter 的结论，RAG 不按执行顺序覆盖；能正面比出的跨通道矛盾要暴露给人工复核，无法比较则记为 cross_channel_undecidable，不能伪装成一致。

3. 只有能重放的结果才写回

finalize_rag_evidence 对接受候选按字段汇总，处理同期间多源异值，构造可被生产 profile 映射重放的 patch，再经 record_structured_evidence 写入 evidence store 和 field check。失败的投影、部分覆盖或冲突不会被降格成 verified；最后仅允许真正 verified 字段关联的原文事实进入“已核实事实”素材池。这样报告中的引用才能回到 source id、locator、原文 quote 与字段状态。

离线案例 RAG：存在组件，不代表它是当前用户上传主路径

先看真实输入边界。load_due_diligence_case() 读取 case manifest 所声明的申请、实体、claims、sources 与 materials，逐项作严格 JSON/JSONL schema 校验，并按 descriptor 校验材料路径与 SHA-256。load_due_diligence_case_package() 再只把已验证 descriptor 所指的字节实体化为 LoadedDueDiligenceCasePackage；下游不再接收 case_root。这是离线材料组件唯一的文件系统入口，且该 loader 明确不读取或导入 oracle。

build_case_material_corpus() 只接受这个已封签 package，以明确的 session_id、case_id、subject_entity_id、截止日构造不可变 corpus。每个 chunk 有 document/material 身份、locator、内容 SHA-256、日期及 eligible_for_structured_evidence 等元数据；组件内检索是确定性的 token 频次排序，结果消费时还会拒绝普通 KB 行、别的 session/case/主体的结果或修改过的摘要/哈希。

接线边界比组件契约更重要。固定基线中 build_case_material_corpus/retrieve_case_materials 只有定义和测试调用，未见被 V2 图、Scout、个人 KB 或 rag_evidence_bridge 调用。因此不能说它“同样会交给桥接校验”或已构成主研究路径；它当前是受控离线案例材料的可复现组件，不依赖个人 KB/Milvus/embedding，也不是管理员上传入口或组织材料产品。

未来若要建设组织 RAG，至少要单独设计材料所有者/可见范围、版本/删除、主体绑定、截止日、索引失败恢复、候选核验和审计；把现有离线组件当作“已上线组织库”会遗漏这些关键责任。

档案 materials：当前可做什么，尚未接什么

当前 search_profile_materials 只先读取一个指定 profile，再将 query 切成词元，在该 profile 自己的 materials 的标题、内容、引用中做“每个词元都是 haystack 子串”的全词元命中；它不是分词边界严格的全词匹配。接口使用一般认证依赖，并非仅管理员可用。结果没有相似度分数，也不枚举其他 profile；每个命中附上来源类型、日期信息，并固定返回 eligible_for_structured_evidence: false。无可检索字符会报验证错误。这是一个隔离的档案查看/检索能力，而不是语义向量检索，更没有自动写入 evidence_store。

要特别区分两条看似相近的说法：“管理员能给企业添加材料”目前成立；“管理员材料已被个人知识库授权检索，并可自动改变尽调评分”目前不成立。研究快照还刻意不携带 materials 正文，因此运行恢复不会把这些自由文本误当作冻结结构化 profile。未来组织 RAG 如果接入，也应以新边界把材料版本、解析状态、权限、主体和候选确认显式建模，不应通过偷偷扩大这一个函数的返回值实现。
