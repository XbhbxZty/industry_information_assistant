Chapter 01 / 先理解系统在解决什么

01　业务目标、参与者与系统边界

这个项目的主线是贷前企业尽职调查：给定一个企业和调查问题，把已有档案与检索材料变成逐项可核对的判断，生成报告，并在需要时交给独立复核人。这里说明的是当前代码怎样模拟这一流程，不是宣称它已经连接银行、税务、征信或能自动批准真实贷款。

理解全项目的关键：它不再只是“搜几篇文章，让模型写报告”。固定清单规定要交代什么，来源与证据决定哪些信息可以采用，规则限制最终评级；模型承担规划、阅读、探索和表达。三者各有职责。

1.1 先把六类业务对象分开

对象回答的问题当前项目中的形状／去向
企业主体调查的是谁？名称、信用代码、档案 ID；管理员档案明确指定时不以模型猜测替代。
业务申请为什么调查、什么场景、什么时点？query、business_type、as_of；档案中的 credit_application、场景数据是另一层。query 提到的金额不能自动算作已验证财务事实。
原始资料别人向我们提供了什么？档案内容、来源记录、材料文本、个人知识库文档、Adapter 响应；进入路径不同，可信条件不同。
事实与证据哪一条信息来自哪里，能否重放核对？facts、field_checks、evidence_store；不能凭对象名字叫 Fact 就把文字当成事实。
风险判断哪些规则触发，信息够不够？scoring_view、risk_assessment、完整度和闸门；不是把模型的一段回答当作唯一评级。
报告与复核决定向人展示什么，谁确认了什么？final_report、复核材料投影和持久化决定；有草稿不等于完成，有完成报告不等于实际放款。

请求字段 · 运行容器 · 风险判断 · 复核决定

1.2 一次研究的端到端阅读路线

① 发起用户身份、问题、档案 ID、检索范围与时点。 ② 装载主体读受控档案或其他主体入口，建立清单。 ③ 收集信息结构化数据源与文本检索采用不同路径。 ④ 文本成为候选召回、抽取、原文与来源核验，不是命中即采用。 ⑤ 核验与报告规则评级、探索性调查、撰写与批判检查。 ⑥ 按条件复核暂停、独立裁决、持久化完成或原决定重试。

这是一张业务阅读图，不是“每个框都必然执行一次”的代码调用图。检索可以关闭；信息不足会留下缺口；Critic 可能要求补搜或修订；人工复核由条件触发。具体条件边在第 06 章，跨请求恢复在第 08 章。

1.3 为什么先定义问题，再找答案

代码的核心清单包含 20 项，其中 15 项必查、5 项选查。它覆盖工商、股权、经营、财务、司法、关联担保和舆情；factoring 场景再追加应收账款等问题。它们是当前代码常量，不是任何现实尽调场景的完整标准。场景扩展不能偷偷删除企业主体的基本核查项。

当前场景扩展项单独统计和展示，不进入核心 verified_rate、by_category、核心评分或闸门。清单里能录入／核验某字段，不等于它已经改变自动评级。见完整度实现，以及评分章的消费边界。
  1. 构造清单骨架：field_id 是机器标识，field_name 是人读的名称，required 表示尽调应交代而非建档必须填满。
  2. 将取得的信息映射到对应项；有依据的值、冲突和未核实分开表达。
  3. 计算完整度，让未取得的信息仍占据应有位置，不因“报告没写”而消失。
  4. 用字段核验结果和规则约束结论；缺口可以导致评级限制或需要人工核查，而不是默认为零风险。
同样是空结果，为什么含义不同？

明确查询过的事件型信息可能合法地没有记录，例如某类事件未查到；登记属性或营业收入为空不能解释成企业没有这些属性。还必须区分“没有启用检索”“服务报错”“能力未实现”和“查询成功但无结果”。项目用 absence_meaningful 等元数据及运行失败信息辅助区分；不能仅凭一个空数组作判断。

清单元数据与空结果语义 · 核心项 · 完整度与闸门

1.4 为什么加入档案和做 RAG 不是重复造轮子

两者处理不同问题：结构化档案描述“当前已录入并带来源的字段”；RAG 帮助从大量文档中找到相关原文。材料解析可以产生候选，但是否变为可供规则消费的值，还要经过字段、主体、日期和来源条件。文件存在不等于交易真实；保存了来源也不等于代码访问签发机构核验过。

本项目的数据边界模拟中可以验证什么不能由此宣称什么
公开信息或年报解析、取证、归属和时点处理覆盖全部企业内部负债或每笔交易真实性
企业／管理员录入字段来源契约、修订审计与冻结消费管理员不会输错，或内部数据已经外部确权
离线案例和 mock 数据源在预设缺口、冲突、风险情形下系统反应是否正确已接上真实征信、银行流水或商业数据 API
人工复核谁对哪份固定材料做了何种决定把不真实的原始材料自动变真，或代替实际信贷审批

因此，想展示 RAG 能力，重点是检索候选如何被验证和拒绝，而不仅是展示一个向量库。更深的组织级材料库接入在本基线仍需另做业务实现，不能因为手册补齐就算功能上线。

1.5 原项目其余页面放在哪里理解

仓库还保留聊天、知识库、记忆、数据库探索、新闻、招投标等页面和服务。它们不是一次 V2 尽调必经的连续节点。前端路由存在、后端注册路由、以及实际研究调用了某个服务，是三种不同证据。

  • 聊天与 V1 研究：属于兼容/其他交互入口；不要用聊天逐 token 的逻辑解释尽调结构化事件。
  • 知识库：作为尽调可以选择的个人材料入口，本书展开其上传到证据链。
  • 数据库探索、记忆、新闻等：属于外围业务功能。数据库页面受管理员守卫控制；本书不把它们冒充当前尽调的实时数据提供者。
  • 后台调度：应用启动会尝试初始化调度和数据检查，不等于所有数据都是请求时实时采集。

实际页面路由 · 后端启动与路由

本章自检：为什么一份完整流畅的报告仍可能不可放行？

报告流畅只说明表达效果。主体是否正确、依据是否有效、清单是否仍有缺口、规则是否触发、复核是否真正完成，都需要各自验证。继续请求入口，不要跳过这些边界。

Chapter 02 / 从点击到服务

02　用户操作如何到达后端

初学时很容易把“前端已经显示成功”和“服务端完成了一次合法写入”当成同一件事。本章按一条请求穿过的边界解释：组件收集输入，API 函数确定协议，请求插件处理通用行为，后端依赖确认身份，Schema 与服务校验数据，然后才执行业务。

2.1 六层分别做什么

层输入 → 输出出问题先查什么
页面／表单选择、输入 → 表单对象或查询选项输入被清空？当前场景？选的是档案还是知识库？
Hook页面动作 → 请求与页面状态变更running、awaiting_review、completed 是否被混用？
API 模块业务参数 → HTTP 地址、正文、响应类型资源接口还是 SSE？是否强制 version=v2、due_diligence=true？
通用请求插件请求配置／响应 → Bearer 令牌、提示和成功失败处理HTTP 已成功，是否却被 envelope 规则误判？
FastAPI 路由与依赖请求／令牌 → 真实用户、数据库 Session、已解析参数401、403、422 发生于哪个责任边界？
业务服务与工作流被允许的数据 → 数据库事务或执行事件来源校验、审计、冻结与规则，不是页面自己决定。

请求实例及插件组装 · 令牌添加 · 尽调 API

2.2 身份不是前端传一个“我是管理员”

  1. 前端认证插件从本地 auth 存储读 token，存在时加入 Authorization: Bearer 请求头。该存储帮助保持登录，不是权限真相来源。
  2. 后端解码令牌，按用户 ID 查实际用户；受保护入口拒绝缺失或无效身份，也检查账号是否启用。
  3. 写档案入口继续依赖 require_superuser，判断数据库用户的 is_superuser。隐藏按钮只是用户体验，不能代替这一层。
  4. 复核入口继续依赖独立复核能力策略；can_human_review 是服务端投影给前端的能力，不是任意用户提交的权限字段。
  5. 检查目标资源：研究 owner 与当前用户、复核者与发起人是否相同、知识库是否属于当前用户。角色允许某类动作，不等于可访问所有资源。
角色／身份档案写入独立人工复核个人知识库研究检索
普通登录用户不允许；可读活动档案无额外能力时不允许按本人的授权范围解析
额外授权复核人不因复核身份获得管理员权限允许处理符合条件的非本人任务不因跨用户看复核材料而获别人的知识库
超级用户允许仍不能审核自己发起的研究该研究检索入口仍不放宽到别人的资料库

额外复核人目前由 DD_HUMAN_REVIEWER_USER_IDS 的 UUID 白名单配置，不是新增了一个通用角色管理平台。策略在进程导入时冻结；配置变化需重启。非法列表会禁用额外授权而非只挑出看起来合法的部分。

2.3 同一个后端接口，调用方默认值也可能不同

ResearchRequest 是后端接收的请求对象；前端 startDueDiligence 会额外设置尽调模式和 V2。不能只看后端字段默认值，猜用户点击按钮后的实际行为。

字段代码语义当前尽调页面
query研究问题，不是经过验证的企业事实非空才允许开始
company_profile_id可选；服务端按 ID 读取内容并冻结可选档案；不直接提交 profile/ref 正文
search_modes只要不是 null，就优先于旧 search_web/search_local 标志不选知识库为 []，选知识库为 ["local"]，无网页搜索开关
as_of研究时点，空表示不设置该时点过滤条件用户可选择；不是数据抓取时间或当前电脑日期

session_id研究身份；已存在的任务不能用新建入口覆盖Hook 生成 dd-时间戳；省略时服务也可生成 UUID
特别容易误读的例子：省略 search_modes 和传 []

后端在 search_modes 不为 null 时直接判断其中是否含 web/local；空数组使二者都 false。省略该字段且不提供旧开关时，后端默认允许 web、不启用 local。但当前尽调前端显式传数组，所以不继承那个 web 默认值。复现问题时应查看实际请求体，而不是只比较界面上有没有选项。

2.4 两类响应和三类错误，不混着解释

建档通常返回普通 JSON 资源；尽调成功建立后持续返回 SSE 事件。status="active" 是档案状态，phase="running" 是界面状态，HTTP 201/409 是协议结果——这些字段名字相近，含义并不相同。

  1. 流开始前错误：鉴权、输入、档案不存在等可用正常 HTTP 错误响应拒绝，页面尚未开始消费研究事件。
  2. 流内执行错误：连接已建立，服务发送 error 事件；不能只看最初 HTTP 200 断定整次研究成功。
  3. 连接自身结束／断开：可能是暂停、取消、正常完成，也可能是中途失败；需要看明确的业务终态。
从一次异常建立排查顺序

先确认 URL 和 HTTP 状态，再确认请求类型。403 检查实际用户与资源归属；422 看字段与领域约束；409 分清版本竞争、已接受另一决定和完整性失败。不要遇到任何 409 都让用户重签，也不要遇到任何 200 都显示完成。具体事件如何落到界面见第 10 章。

资源响应曾被误判的地方 · 复核错误响应保留 · 档案失败矩阵

本章自检：给前端用户对象加 is_superuser=true 能取得权限吗？

不能。它最多影响界面展示；后端还要验证 token、真实数据库用户和具体资源条件。若界面误显示入口，正确的后端仍应拒绝请求。相反，合法复核人能看最小复核包，也不能据此读取别人的完整检查点。
