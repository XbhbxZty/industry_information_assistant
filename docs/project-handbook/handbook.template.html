    02 / 深入一条真实链路

    样章：一份管理员档案，如何成为固定的尽调输入

    这条链路有两个不同的请求：管理员先保存档案；普通用户随后选择档案发起研究。保存档案本身不会启动尽调，读取档案也不等于已经得出风险结论。

    1. 管理员填写表单 → 后端授权与校验 → 当前档案与审计同事务保存。
    2. 用户选择档案 ID 发起研究 → 从数据库读取并校验 → 冻结快照进入工作流。
    这里冻结的是“研究所用的结构化档案投影”。补充材料保存在管理档案中，但当前快照不会把它们的正文复制进研究状态。它不是完整企业材料库，也不是上传文件后自动进行组织级 RAG。见材料边界。
    输入与保存步骤 1–3：前端、校验、事务读取与解释步骤 4–6：ID、快照、事实与清单版本与恢复步骤 7：当前档案变了，旧研究怎么办

    样章 / 1　输入

    1. 前端表单：让业务输入变成明确的请求

    源码核对

    入口是 /company-profiles/new。表单分成主体与场景、工商与股权、财务与业务、司法担保关联、来源与材料。记录列表允许添加股东、财务期间等；不是把整份企业情况塞进一个大文本框。

    1. 读取服务端模板。核心清单、场景字段和字段输入类型由 /company-profiles/templates 提供。前端用模板渲染“尽调必查”标签与来源覆盖选择项，不能自己决定哪些项算必查。
    2. 填写或暂留空白。企业名称是唯一创建必填业务字段。若你添加一条股东记录，该记录的名称和比例等仍需满足自己的要求；若填了场景值，还必须有覆盖该字段的来源。可不提供一类资料 ≠ 可以提交一条残缺的资料记录。
    3. 切换场景。当前支持通用（空字符串）和 factoring。切换时清空场景数据，并过滤不适用于新场景的来源覆盖字段。正文中明确说明这个动作，避免误以为切换只改展示。
    4. 提交前清洗。normaliseDraft 去除空场景值、处理可选文本，并去掉材料响应中的只读 eligible_for_structured_evidence。它不负责认定来源真实性。
    5. 选择创建或修改请求。新建发 POST；修改发 PUT，附带当前 revision 和必填修改原因。成功后才跳转档案详情。创建页面当前不提交修改原因字段，服务端使用创建原因默认值。
    展开：最小合法创建请求，以及响应里多了什么

    下面是可以表达“先建一个壳，稍后补资料”的请求格式。公司名称为合成示例；这里只展示数据，不发送请求。

    {
  "profile": { "name": "示例澄川设备有限公司" }
}

    Pydantic 补上默认值：scenario: ""、空的 scenario_data、field_sources 和 materials；创建原因也有默认值。经过服务端准备后，profile.coverage.queried 是空列表，不是“全部查过”。

    成功响应是档案资源，包括服务端生成的 id、revision: 1、status: "active"、内容摘要和时间。数据库 ID 与哈希由后端生成，本页不伪造一份声称已经落库的完整响应。

    为什么保存成功还可能被前端当成失败？

    本项目曾把所有响应顶层 status 都当作 API envelope，要求等于 success。档案资源却使用 active / archived 表示资源状态。现在仅四个档案资源接口声明 responseStatusIsResourceState，保留原 HTTP 错误，不再误判成功结果。见拦截器与DEV-BC-20260902-028。

    样章 / 2　输入边界

    2. 后端不是直接把表单写进数据库

    这里有不同性质的校验。鉴权依赖和请求解析都由 FastAPI 处理；它们不是供客户端依赖的固定错误优先级协议。下表按责任拆解，不声称所有无效输入总先得到同一个错误。

    边界具体检查它不证明什么
    身份与权限解析令牌、查实际用户、要求账号有效；写接口依赖 require_superuser。前端展示了按钮不代表后端授权成功。
    Pydantic 请求结构外层请求及来源/材料对象的类型、长度、枚举和额外字段；场景只能通用或保理；修改须带版本与原因。profile 与 scenario_data 是 Dict[str, Any]，内部业务规则交给下一层领域校验。JSON 结构正确不代表其中事实可信。
    业务内容准备规范化、校验字段来源、重建 coverage，按生产映射试算哪些项会变成 verified。管理员声明来源类型不等于系统实际访问了原机关或银行核验真伪。
    深入：prepare_company_profile_content 的八个子过程
    1. 复制与名称规范化：要求 profile 为 JSON 对象、名称非空；禁止客户端提交自定义 required；空信用代码不保留，非空只去首尾空白并转大写。当前 18 位字母数字规则在前端表单，服务端并未验证格式或校验位；不能将前端限制误当成 API 保证。
    2. 确认场景及字段集合：场景只能是 "" 或 factoring；scenario_data 不能混入其他场景的键。
    3. 检查 field_sources：来源 ID 唯一，名称、签发者、引用齐备；只接受 official/authorized/audited；覆盖字段须属于当前清单；取证日期与事实日期不能矛盾，提供的摘要须满足格式。
    4. 检查 materials：限制条数和文本长度；只接受企业提交/管理员观察；材料日期与未知日期原因二选一；补生成材料 ID，并强制标记不具备结构化证据资格。
    5. 检查场景值覆盖：主动填写的场景字段必须被受信来源明确覆盖；不能用一条“这是官方资料”的笼统备注代替字段级关联。
    6. 重建 coverage：抛弃客户端传入的 coverage；从来源的 field_ids 合并出 queried，并采用最早取证时间作为这一层汇总时间。后续逐字段来源的时点处理是另一层，不应混为一谈。
    7. 复用生产映射检查：调用 profile 结构校验、构建清单、profile_to_facts 与 fill_field_checks。任何会被投影成 verified 的字段，都必须出现在覆盖集合中；否则拒绝保存。
    8. 计算内容摘要：对规范化后的 profile、scenario、scenario_data、field_sources、materials 计算 content_sha256，供保存与后续核对。此时还未提交数据库。

  "profile": {
    "name": "示例澄川设备有限公司",
    "registration": { "company_type": "有限责任公司", "operating_status": "存续" }
  },
  "field_sources": [{

    样章 / 3　持久化

    3. 当前档案与审计，必须一起成为已提交数据

    后端获得规范化内容后，新建 AdminCompanyProfile，初始 status="active"、revision=1。创建人来自当前登录用户，不接受前端代填。

    1. add / flush：把当前行放入本次 SQLAlchemy 事务并 flush 到数据库，获得记录 ID。flush 不是 commit，不能把它当成最终保存成功。
    2. 追加审计：_append_audit 记录动作、操作者、原因、修订号、前后快照摘要与上一个链节点的 MAC。新建时 before 为 null，after 是新档案快照。
    3. 签发并更新链头：使用审计 keyring 签发记录；把最新 MAC 和快照摘要写回当前档案行。HMAC 是有密钥的完整性验证，不是加密。
    4. 再次 flush 并验证审计历史：检查结构、领域快照、签名链和当前行一致性。它不是只检查某个哈希字符串是否存在。
    5. commit 后返回：提交事务、刷新对象，再由 API 投影成公开响应。遇到数据库约束或事务异常会 rollback；不能只留下档案而漏掉对应审计。

    当前行：方便读取最新版本

    admin_company_profiles 保存当前 profile_json、场景、来源、材料、状态、版本和审计链头。它不等于一条聊天消息。

    看字段与用途 →

    历史行：记录每次变化

    admin_company_profile_audits 保存各修订的 before/after 和签名信息。旧历史还有独立 anchor 机制，不是事后假装所有旧记录从一开始都已签名。

    看签发过程 →
    不进入个人知识库。这一保存函数没有创建 KnowledgeBase、Document 或 Milvus collection。企业补充文本属于档案 materials；个人资料库是另一条上传、存储和授权路径。全局档案也不代表互联网公开，读取接口仍要求登录。
    正常保存和“响应丢失”不是同一件事

    上述事务保证档案与审计一起提交。但网络可能在提交后、客户端收到结果前断开。这里不能因此宣称“创建接口天然幂等”。本项目复核决定的持久化幂等有专用协议，详见计划中的人工复核章；不要把那一套保证自动套用到创建接口。

    样章 / 4　从记录到研究输入

    4. 发起尽调：传的是档案 ID，实际内容由后端读取

    尽调页面分别加载企业档案列表和个人知识库列表。选中档案会帮助填写问题文本；请求中真正定位档案的是 company_profile_id，不是模型从名称里猜出的对象。

    {
  "query": "请对示例澄川设备有限公司做贷前尽职调查",
  "version": "v2",
  "due_diligence": true,
  "company_profile_id": "11111111-1111-4111-8111-111111111111",
  "as_of": "2026-08-27",
  "search_modes": []
}

    这是精简请求形状。ID 为占位示例，实际需使用创建接口返回的 ID；前端还会生成 session_id。这个请求不会在文档中执行。search_modes 为空表示不启用该请求的外网／个人知识库搜索，不妨碍指定档案被读取。

    当前尽调页面未选资料库时传 []，选中资料库时传 ["local"]；该页面没有发起 ["web"] 的操作。URL 里带来的档案 ID 即使不在列表中，也可能被继续提交；是否存在、是否已归档，最终由流前服务端检查并返回 404。

    深入：为什么要在 StreamingResponse 之前完成读取
    1. 验证登录和已有 session_id 的访问/重复使用条件；创建 V2 服务。
    2. 显式提供档案 ID 时调用 _load_admin_company_profile_snapshot，由唯一档案服务读取有效记录；不存在、已归档、坏审计或缺少验证密钥分别报错。
    3. get_company_profile 在返回前验证审计历史；get_active_profile_snapshot 再按保存内容重算摘要并重新运行领域准备校验。
    4. 构建 {profile, ref, scenario}。profile 带三个内部附加字段；ref 只有 ID、修订号、内容摘要、来源标识。
    5. 路由用 JSON 序列化/反序列化再复制一次，拒绝非 JSON、NaN 等内容，切断与 ORM 活对象的引用关系并确认顶层形状。
    6. 单独解析当前用户的个人知识库授权范围 kb_scope；选择企业档案不会授予别人的知识库权限。
    7. 之后才返回 SSE 响应，并把已取好的快照传给工作流。此时档案错误可以作为普通 HTTP 错误返回，不必等流打开后再发现。
    显式 ID 无效时，系统不会回退为同名静态公司。因为“你指定的 A 档案没找到”和“我替你找一个名字近似的 B 档案”不是同一个任务。未指定管理档案时，原有名称匹配或动态主体路径仍存在。

    样章 / 5　状态初始化

    5. “冻结”不是只记一个版本号

    只保存 profile_id，恢复时再去查最新档案，会把后来录入的资料混进之前的判断。所以状态里既保留实际采用的结构化内容，也保留它来自哪个版本的引用。

    1. 分离对象引用。create_initial_state 再次深拷贝 profile 和 ref。后续修改数据库记录或调用方对象，不会直接修改这份研究内的副本。
    2. 计算运行投影摘要。对复制后的 profile 计算 admin_profile_payload_sha256。它和数据库的 content_sha256 覆盖内容不同，见六项完整性机制。
    3. 绑定研究身份。签发 admin_profile_snapshot_binding，把 session_id、profile、ref 和 scenario 绑定在一起。支持带 key ID 的配置，具体格式由当前 keyring 决定，不能硬写成所有环境固定一个版本。
    4. 初始化工作容器。provided_company_profile 和 admin_profile_ref 保存冻结输入；company_profile、facts、field_checks、evidence_store、scoring_view 等先为空，等待后续各层填充。它们不是此时就全部可信或全部有值。
    5. 选定完整性模式。有管理档案快照时进入管理档案模式；后续图保存与恢复会继续验签。内存里的 deepcopy 本身不具备跨进程持久性，跨重启依赖之后的检查点存储。

    六项机制，不能用“都是哈希”一笔带过

    名称主要覆盖内容／目的验证边界
    content_sha256数据库五块规范化业务内容：profile、scenario、scenario_data、field_sources、materials。包括不进入研究投影的材料；不能仅凭研究 profile 重算它。
    snapshot_sha256（审计快照摘要）完整审计快照，包括 id、name、status、revision 和五块业务内容等。不同于内容摘要；归档可以不改业务内容，却会改变完整审计快照。仍是无密钥摘要。
    admin_profile_payload_sha256本次研究携带的装饰后 profile 内容。检测投影变化；普通摘要本身不证明是谁签发。
    admin_profile_snapshot_binding用 HMAC 将 profile、ref、scenario 与本次 session_id 关联。防止把有效的管理端快照投影改绑到另一任务或替换绑定内容；不直接携带、逐项验证 materials 正文。
    审计记录 HMAC 链覆盖操作人、原因、修订、前后快照摘要和前序 MAC 等，保护档案修订历史。与普通 SHA-256 不同，验证需要受控密钥；数据库中的链头并非外部单调锚点，不能单独保证抵御整库回滚。
    图状态 seal（封签）保护节点边界的图状态，保存与恢复时校验。不能代替业务检查点完整性记录或档案审计链；它们都不证明原始事实真实。

    依据：状态初始化 · 快照绑定签发/验签 · 运行投影校验及两种摘要说明 · 审计快照摘要 · 审计快照具体字段

    样章 / 6　进入现有尽调机制

    6. 冻结内容如何变成事实和核查项

    _load_company_profile 优先检查显式管理档案快照。必须同时有 profile 与 ref；验证后才把它认作本次主体。源码顶部有历史版本说明，不能据此断言今天只会读取硬编码 JSON。

    1. 校验投影及引用。核对 ref 形状、摘要、内嵌 _admin_profile_ref 一致性，以及场景和来源附加字段。通过后重新签发进程内授权标记；不能仅凭客户端或存储中的一个布尔标志信任内容。
    2. 写入可消费档案。设置主体名、company_profile 与 credit_context。company_profile 是用于后续确定性投影的结构化对象，不是最终报告。
    3. 转换事实。profile_to_facts 将已有结构化信息转换为 facts 记录。不会因为模板要求某项就替缺失信息编造值。
    4. 构建并填充清单。确定业务场景，生成固定核心清单和场景项，调用 fill_field_checks 填值、状态及逐字段来源，再统计完整度。
    5. 接入结构化 Adapter。复用原 apply_all 路径补充档案未覆盖的项；代码注释和实现边界强调不能仅凭“后执行”覆盖已经核实的结论。此处的每个 Adapter 内部过程留给第 04 章展开。
    6. 交给后续分析。事实、清单、证据及后续构造的评分视图被后续节点使用。这里不是直接把整个原始档案交给模型“自由决定风险等级”。

    facts：表达“有哪条信息”

    内容、来源与事实 ID 等帮助叙述和引用。一段自然语言本身无法替代所有可重放的数值和核验状态。

    field_checks：表达“每项查得怎么样”

    固定字段、状态、值、来源、失败原因等。即使没有事实，也应能看到该项缺口，避免从报告里消失。

    字段与消费者 →
    “与 company / adapter 同等效力”指进入同一套尽调消费与验证机制，不是来源形式完全相同。管理档案可保留字段级 profile_sources；Adapter 证据有 evidence_ids 等自己的路径。不能要求所有来源都长成同一个字典，也不能允许一种来源绕过判断边界。
    必须分清：三类材料能力目前没有自动合为一体

    • 个人知识库：另有文档上传、索引与用户权限范围。发起时选择资料库才走相应授权检索；选择企业档案并不自动把它们合并。
    • 仿真案例离线检索／未来组织材料库：已有离线案例组件不等于管理档案已经接上组织级向量检索。组织级上传、材料版本、候选证据确认写回属于后续能力。

    这不是说“RAG 不适合尽调”，而是说明当前哪些路径已经接线。把检索候选提升为结构化证据，需要明确主体、原文、日期和来源条件；深入讲解安排在第 05 章。

    样章 / 7　时间与版本

    7. 当前档案改了，为什么旧研究不跟着改

    修改接口携带 expected_revision。服务先检查当前版本，再执行带 ID、active 状态和旧版本条件的 UPDATE，并检查更新结果；成功后版本加一并追加审计。这个条件更新用于防止两个管理员把彼此的修改悄悄覆盖。

    档案 revision 是“这份企业档案修订了几次”；研究检查点还有自己的业务版本。二者不是同一个计数器。复核完成增加检查点业务版本，不代表管理员又修改了一次档案。

    沿时间看一遍

    下面只切换解释用的静态示意数据，不会读取数据库、创建任务或执行恢复。这里的 v1/v2 指档案修订，不是研究接口版本。

    数据库当前档案

    profile_id: demo-profile
revision: 1
name: 示例澄川设备有限公司

    原研究采用的快照

    研究开始时保存内容副本与 ref；此刻当前档案与研究输入都对应修订 1。

    恢复不是无条件相信已保存的 JSON
    1. 先确认检查点完整性模式；管理档案痕迹不能被当作普通旧静态任务绕过检查。
    2. 按恢复路径要求校验图状态封签；确认当前 session_id 与保存的任务一致。
    3. 校验冻结 profile/ref/scenario 与 HMAC 绑定；缺失或不一致就拒绝，不读取最新档案“自动补好”。
    4. 重新验证管理档案投影、重建授权标记，并核对已保存 company_profile 与已验证的规范对象一致。
    5. 继续重建/核验清单、证据与评分输入，只有通过后才继续恢复执行。完整人审 claim、最终事务和幂等回放将在第 09 章单独拆解。

    跨重启成立还依赖后续图检查点和业务检查点实际持久化。_save_checkpoint 在交给业务保存服务前刷新图状态封签。最近的独立进程验收使用真实 PG 图检查点，验证了更新当前档案后重启，复核包仍引用旧版本；这不等同浏览器交互已测。

    03 / 数据字典

    同一份内容，为什么会有不同的数据形状

    表单对象、API 请求、ORM 当前行、研究快照和运行状态不是同一个对象的不同名字。每次转换都有保留、补充或舍弃的信息。下面按这条样章的生命周期解释；全量字段字典留给后续章节继续扩充。

    ① 写入契约：CompanyProfileCreate / Update

    由前端生成，Pydantic 接收，再由内容准备函数规范化。创建与修改共用核心内容；修改是整份替换，不是随意发送一个字段的 PATCH。

    字段类型／缺省含义与去向
    profile对象；name 必须非空主体结构化字段，后续成为 profile_json 与研究投影基础。
    scenario"" 或 "factoring"选择清单扩展；不是由模型自由创建场景。
    scenario_data对象，默认空仅所选场景键；填值需有对应字段来源。数值单位需按具体字段解释，不能把所有金额默认当同一单位。
    field_sources来源数组，默认空来源 ID、类型、覆盖 field_ids、日期与引用。
    materials补充材料数组，默认空正文与材料日期；不自动进入结构化核验。
    expected_revision仅修改要求，整数 ≥1声明你编辑的是哪个版本；服务器做并发比较。
    change_reason创建有默认；修改必填进入审计记录，不是事实字段。

    Pydantic 定义 · 来源与材料子结构 · 创建者：表单 · 消费者：服务校验

    ② 持久化当前行：AdminCompanyProfile

    create/update 服务写入，档案详情与研究快照服务读取。profile_json、scenario_data、field_sources、materials 为 JSON 列；name/credit_code 另有查询列。这里不能用旧说明里的数据库表总数推断现有模型。

    • id：档案身份；改版本不换 ID。
    • revision：本档案修订号；创建为 1，修改/归档递增。
    • status：active/archived。归档不是物理删除，旧审计仍保留；但它是本档案审计链的终态，不能再修改，当前没有取消归档接口。本章“恢复”指研究检查点恢复，不是重新激活档案。
    • content_sha256：五块规范化业务内容摘要；这些内容变化时重算。状态与修订号不在其覆盖内，归档通常不改变此摘要。
    • audit_head_mac / audit_head_snapshot_sha256：对照审计链的当前头，不是对外材料的真实性证明。
    • created_by / updated_by 与时间：服务端记录操作者和时间；普通读取会按响应投影限制操作者信息。

    模型定义 · 归档终态 · 创建过程 · 修改过程 · 响应投影入口

    ③ 读取投影：{ profile, ref, scenario }

    由 get_active_profile_snapshot 创建，路由复制，状态初始化和图加载消费。以下是结构示意，不是可提交请求；尖括号内容表示运行时值。

    {

    "name": "示例澄川设备有限公司",

    "_admin_profile_ref": { "id": "<实际档案ID>", "revision": 1,
      "content_sha256": "<64位内容摘要>", "source": "admin_company_profile" },
    "_scenario_data": {},

    ④ 运行容器：ResearchState 的相关部分

    状态字段谁创建／修改为什么存在
    provided_company_profile初始化深拷贝；作为冻结输入核对保留服务端读到的实际投影。
    admin_profile_ref / admin_profile_scenario初始化复制绑定来源版本与场景；SSE/复核材料可展示公开引用。
    admin_profile_payload_sha256 / admin_profile_snapshot_binding初始化计算／签发支持之后检查投影和任务绑定。
    company_profile图加载校验后填充供生产映射、证据重放等消费的规范化档案。
    facts档案投影和后续相关节点生成事实条目集合，不替代固定清单。
    field_checks / completeness清单构建、填充、核验和统计把已知、未知、冲突显式表达。
    evidence_store / scoring_view证据处理与验证层逐步构建支撑可追溯判断与受控评分输入；不是原始文本直接打分。

    表中是相关字段的责任概览，不是完整 ResearchState。TypedDict 用于表达预期字典形状，本身不是自动运行时验证器。

    初始化时的实际值 · 下游怎样填充 · 恢复时怎样复核

    ⑤ 单个核查项：FieldCheck

    清单先创建骨架，再由档案、Adapter 或合格证据填充。DataAnalyst 的判断、完整度统计、前端清单和人工复核都需要理解它。相关字段：

    • field_id / field_name / required：检查什么、叫什么、是否属于尽调必查。
    • status / value：本项核实状态和相应值。unverified 不表示业务事实不存在；不要仅凭这一状态反推具体是否查询过，应再看 attempted_sources 和 failure_reason。
    • sources：关联事实 ID；不等于整个证据正文。
    • verification_origin / evidence_ids / source_adapter：核实来源和证据索引，按实际来源路径使用。
    • profile_sources：管理档案逐字段来源投影；只带覆盖这一字段的来源身份与时点，不带另一层的 field_ids 声明列表。
    • retrieved_at / as_of_date：取证时间与事实日期，不能互换。

    空值、零值、已核实无记录是三回事。空值可能是缺资料；零可以是一个有来源的真实数值；无记录必须来自明确查过的结果。当前哪些字段允许哪些状态，以各字段映射和核验规则为准。

    04 / 不只讲成功

    失败在哪一层，应该先看什么

    下面是本样章路径的典型分支，不是所有 API 的全局错误码规范。HTTP 状态相同也可能有不同原因，要连同响应说明和处理位置判断。

    现象失败边界／含义先查这里
    401未登录、令牌无效等鉴权失败；不是企业资料缺失。用户依赖
    403有效普通用户尝试写档案，或其他权限拒绝。管理员判定
    422写请求不符合 Schema 或领域要求，如记录残缺、来源覆盖不足、日期不合法。准备函数子过程
    409：修改冲突expected_revision 已旧，或数据库约束拒绝写入。先重新核对当前档案，不要盲目覆盖。版本条件更新
    409：读取/发起完整性失败档案与审计不一致或摘要校验失败。不能当普通版本冲突自动重签“修复”。错误映射、审计验证
    404：发起时找不到档案ID 不存在或档案已归档，不回退名称匹配。快照读取
    503：历史验证密钥不可用服务无法验证已存签名；不能临时跳过验证继续用数据。发起时映射、密钥章
    恢复报快照、绑定或派生状态不一致冻结快照、任务身份或派生状态不匹配。拒绝降级成静态任务或最新版本。恢复核对顺序
    HTTP 成功但界面报错曾出现资源 status 被通用插件误当成 API 错误的 Bad Case。插件、修复记录
    如果我自己排查，按什么顺序看？
    1. 先辨认失败的是保存档案还是发起研究，是否已经打开 SSE。
    2. 检查请求体属于哪个 Schema；不要把响应的只读字段原样回发。
    3. 核对登录用户和实际权限，不以菜单是否可见为依据。
    4. 核对 ID、expected_revision、来源覆盖与日期；材料缺失和证据冲突分别看。
    5. 如果进入完整性失败，不直接改数据库或重算摘要掩盖问题；先查签名/版本/审计是否一致。
    6. 使用相关测试定位层级。页面效果、接口行为、真实数据库与真实模型是不同验证范围。

    发生位置：表单 →
    profile：结构化档案

    以字段和记录表达企业信息。与一份 PDF、补充文本、检索片段或最终报告不是一回事。

    看它的不同形状 →
    coverage：来源覆盖声明

    保存前由服务端重建，而非相信客户端自报。queried 由来源覆盖字段合并；声明覆盖并不等于所有字段有值、都已 verified，更不等于现实中绝无风险。

    看重建过程 →
    field_sources：字段级来源

    说明哪些来源支持哪些字段，附带来源类型、签发者、取证时间、事实日期和引用。来源记录与字段之间是明确关联，不是全文最后笼统列几个网址。

    看合成 JSON →
    materials：补充材料

    当前管理档案中用于阅读和受控关键词检索的补充文本。不自动具备结构化证据资格，不因为被录入就直接进入评分。

    查看三类材料的边界 →
    Schema 与 TypedDict

    Pydantic Schema 在请求/响应边界执行验证和序列化。TypedDict 描述预期字典形状，不会单凭声明自动验证所有运行时数据。两者都不能单独证明事实真实性。

    请求 Schema → · 运行状态 →
    ORM 与 Session

    ORM 将 Python 模型映射到数据库表。SQLAlchemy Session 管理查询和事务中的对象；研究快照要脱离这样的活对象，转成可保存的纯 JSON。

    保存 → · 读取投影 →
    事务、flush、commit、rollback

    事务把一组相关写入作为一个提交单元。flush 把待写数据送到数据库但尚未最终提交；commit 成功后才完成提交；rollback 撤销未提交事务。本例要求档案和审计一起保存。

    查看五步写入 →
    revision 与条件更新

    revision 是档案修订号；expected_revision 表示编辑者基于的版本。UPDATE 同时匹配旧版本，避免后来提交的人静默覆盖别人。档案版本不是研究检查点业务版本。

    看版本时间线 →
    快照与冻结

    保存某个时点实际采用的数据副本和来源版本，不仅是保存一个可再次查询的 ID。内存副本只解决引用变化；跨进程恢复还依赖持久化和完整性校验。

    进入冻结过程 →
    SHA-256：内容摘要

    把指定内容算成摘要，用于检测两份内容是否一致。没有秘密密钥，能够修改内容的人通常也能重算摘要，所以它不能单独证明内容来自可信签发者。

    看本项目几种摘要 →
    HMAC、封签与 keyring

    HMAC 用秘密密钥验证内容未被无密钥者任意改写。keyring 管理签发/历史验证用的密钥与 key ID。它不是内容加密，不证明外部事实真实，也不抵御同时拿到数据库和签名密钥的攻击者。

    分别保护什么 →
    facts：事实条目集合

    描述所得到的信息、来源和引用身份。不要仅凭它叫 Fact 就认为任何检索文本都已通过核验；还要看进入路径和清单/证据层的验证结果。

    看它如何产生 →
    field_checks：核实清单

    为每项问题显式保存状态、值和依据。unverified 不能翻译成不存在；具体为何未知要看失败原因和尝试记录。

    看字段及生命周期 →
    evidence_store：证据索引容器

    供核验/重放使用的证据集合，与 facts 的自然语言记录和 RAG 的原始命中不是同一层。来源路径不同，对应引用字段也不同。

    本章消费位置 → · 后续深讲 →
    scoring_view：受控评分输入

    评分需要经过验证的字段视图，不是任意模型文字或材料正文。它如何构建、如何处理不足和冲突，将在核验与风险章详细拆解。

    进入章节目录 →
    SSE：持续返回事件

    一次 HTTP 响应可以持续发送事件。流前失败可返回普通错误状态；流打开后则要看事件。连接结束不自动等于研究完成。

    流前快照读取 → · 前端消费章 →
    两类检查点

    工作流检查点保存图执行所需状态；业务检查点保存应用读取、报告和权限等业务状态。不是同一张表，也不能只保存其中一处就声称所有恢复场景都成立。

    本章恢复边界 → · 后续存储章 →
    RAG：检索增强生成

    先检索相关材料，再让后续处理利用它。检索相关性不等于真实性；本项目还需要主体、日期、字段和证据条件。当前关键词检索与未来组织级向量库不要混称。

    本章实际边界 →
    fail-closed：验证失败就拒绝

    发现指定档案损坏时停止使用，不偷偷换最新版本、同名公司或无签名旧状态。它保护判断依据，但不等于系统永不出错或能够自动修复数据。

    读完能回答这些问题，就真正理解了本章

    1. 为什么公司名称能先建档，而填写登记状态后却可能保存失败？

    创建允许信息缺失；主动提供的值如果会成为 verified，则必须满足来源覆盖等条件。两者是不同约束。回到来源覆盖子过程。

    2. content_sha256 为什么不能从研究 profile 直接重算？

    数据库摘要还包括 materials 等内容，研究投影故意不携带补充材料正文。运行投影另有 payload 摘要，二者不能混用。看摘要对照表。

    3. 如果管理员在研究途中更新了档案，旧研究恢复时应读哪里？

    使用原研究保存并通过完整性检查的冻结内容，不重新查询最新档案替换。深拷贝避免内存引用污染，持久化与验签支持跨进程恢复。看时间线与恢复。

    4. 页面隐藏编辑按钮后，为什么还需要 require_superuser？

    用户可以绕过页面直接发 HTTP 请求。菜单是体验层，后端用户依赖才是接口权限边界。看实际用户验证。

    5. 给企业添加一条补充说明，为什么不能说“它已经进入 RAG 风险评分”？

    当前材料保存在独立档案字段，提供档案级关键词检索，结构化资格固定 false，研究快照不携带它的正文。组织级材料检索与候选确认尚未接通。看材料边界。

    6. 我要新增一个可用于尽调判断的字段，应该检查哪些位置？

    先确定业务语义、单位和空值含义；检查清单定义、输入 Schema/模板、表单、来源覆盖、档案映射、证据验证、评分消费者、状态与响应、测试。哪些需要实际修改必须依据该字段的职责核对，不能只在页面加一个输入框。后续开发与验证章会给完整案例。

    样章反馈重点：哪一步你仍无法从输入推导输出？哪个词条解释不够？源码片段是否足以找到逻辑？这些反馈用于调整全书深度，而不是先把十二章都写成同一种不合适的密度。
