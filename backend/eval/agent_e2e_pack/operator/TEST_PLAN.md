## 采集与失败处理

每次记录：run_id、Git提交、账号代号、库ID、文件清单、模型、模式、请求中的as_of/search_modes、起止时间、最终状态、调用次数（若日志可见）、首个失败阶段。保存报告、事件截图或脱敏SSE。不得保存令牌、密码、Cookie或真实用户数据。

- 上传失败：保存错误和后端日志；暂停效果评分。
- 解析成功但无命中：检查库选择与索引；标记检索失败，不责怪模型没找到事实。
- `stalled`/`step_limit`/`time_limit`：可以评分已产出内容，但运行完成项不通过；保留状态，不改成成功。
- 进入人工复核：流程可视为抵达合法终点；只验收暂停与任务可见，不要求批准。
- 无网络场景出现网页搜索：来源控制失败；不要以外网补齐资料掩盖问题。

## 对比方法

先各跑1次排除链路故障，再各跑3次；顺序交替（标准→自主，自主→标准，标准→自主）。使用同一输入、索引、截止日、模型配置，记录不同模式调用数和耗时差异；不要只挑最好的一次。

内容质量按ORACLE的10项计分，另报正常终止率、硬失败率与中位耗时。关键词出现不等于推理正确。建议首轮目标：T01每次至少8/10且无硬失败；三次中至少两次正常终止。此阈值是开发验收目标，不是统计显著性或上线证明。

未实现的能力（例如补件后自动恢复原会话）不伪装成通过：T03是全新会话重新调查，再与T01人工比较，并不测试自动续跑。
