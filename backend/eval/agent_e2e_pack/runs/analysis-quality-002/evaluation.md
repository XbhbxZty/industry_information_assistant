# 分析复核协议与真实修订闭环：开发验证

这不是 T01 端到端成绩，也不是上线可靠性证明。测试只发送脚本内虚构案例，不读取业务数据库；没有放宽证据门槛、提高生产 token 预算或替换模型。

## 实验与已知失败

四类定向案例：错误同比归因、回款漏算、正确计算并披露限制、资料不足且明确披露不可计算。每类重复两次，模型均为配置中的 deepseek-v4-flash、温度 0、输出上限 8000。上次 analysis-quality-001 脚本的 4000 上限不是生产配置，不能与此处混算。

| 版本 | 次数 | 复核不完整 | 无错误/已披露限制案例通过 | 调用耗时中位数 |
| --- | ---: | ---: | ---: | ---: |
| 原协议，baseline.json | 8 | 4 | 2/4 | 37.350 秒 |
| 紧凑协议二版，compact-v2.json | 8 | 1 | 3/4 | 23.564 秒 |

两组对四个错误输入均产生了针对目标错误的 issue，但原协议其中三次还存在其他检查项格式或引文问题，不能把“出现了正确告警”等同于完整复核成功。

二版仍有一次把四个固定检查项 ID 改成 q1/p1/c1/r1，按协议失败阻断；没有做猜测映射。以上样本很小且在开发中使用，不能当作独立盲测或统计显著性证明。

中间还有一版压缩了审核约束的 8 次试验：格式失败为 0，但同比归因漏判一次，故未采用该版。正确与披露限制案例 4/4 通过不能抵消这次漏判。该轮完整响应只在当时工具输出中出现，中断后未保留原始文件；这里仅保留观察摘要，不伪造原始响应。

## 带引文的闭环复测（与上表分开）

`revision.json`：

- 归因例被识别，但 Writer 输出未通过校验，旧记录得到保留，复核仍阻断。
- 回款例漏判。检查后发现模型把引文中完整的分类数据当成了报告已经正确归纳的结论；Writer 实际未调用，不能计为修订成功。

`revision-separated-claims.json`：

- 将待审 claim/summary 与 quote/source 分开提供、明确原文正确不能补救错误概述后，两例均被识别。
- 回款例完成真实 Writer 修订并通过再审核：期末应收回款改为 130（90+40），另有预收 70，总计 200；长账龄剩余 160、覆盖率 36%。原引文、来源、核查状态和评级未变。
- 归因例 Writer 写出超过 700 字的单条发现，触发 `修订发现长度无效`；这不是 JSON 截断或资料丢失。拒绝后原记录保留，不误标为修订成功。

因此再将 Writer 输出限定为可直接替换的简洁结论（目标 30–200 字），保留原有 700 字硬上限，不通过截断文字或放宽门槛冒充成功。最终复测另存文件，不能覆盖上述失败。

## 实现边界

- 只对自主尽调使用紧凑审核协议；普通工作流仍使用既有协议。
- 保留原有审核原则；量化错误只写在四项检查中，避免重复生成多份 issue。
- 严格拒绝重复 JSON 键、错层字段、错误检查项、非有限评分、无法定位的违规引文；不推测性修补为通过。
- 使用 finish_reason 拒绝截断/过滤响应，即便部分 JSON 恰好能解析。
- 每次审核只有一次有界模型调用，无 SDK 重试；调用元数据随复核事件保留，不采集内部思维过程。
- 修订只能改变 AI 分析，不得改原始证据、核查或评级；后续完整复核通过后才关闭旧分析/协议问题。
- 字段抽取超时等其他问题并未由此消除。

## 最终简洁修订复测

`revision-final.json` 对应生产代码提交 `17657e8`：两条错误均先被识别，实际调用 Writer 后通过再审核；两例均无修订错误，保护字段保持不变。归因例明确撤销缺少上期调节项时的同比贡献/主因判断；回款例补齐短账龄 40、总收款 200 的分类。没有把此前失败从统计中删除。

这是对两个开发案例各一次的闭环确认，不是泛化或稳定性证明，也不覆盖真实上传、检索和审批流程。
