# 第三套盲测（v4）：确定性扫描器的删除依据（2026-08-13）

## 结论

**确定性扫描器 `service/claim_scanner.py` 及其门控、强制分工、提示词注入
四条通道全部删除。** 依据是它在未见数据上零独有收益、且有可度量的净损失。

v0.5 仍未质量封板：A 组（生产候选）误报 33.3%、2 个稳定失败，
不满足运行前固定的封板条件。BC-29（严重度与裁决不一致）亦未修。

## 删除依据：扫描器零独有收益，且倒扣

逐用例比对 A 与 B 的检出结果：

```
A 比 B 检出更好的注入用例：无
B 比 A 检出更好的注入用例：BLD4-INJ-01、02、10、11
```

扫描器在本集合上**唯一**命中的注入用例是 `BLD4-INJ-08`，
而 B 组（无扫描器）对同一例 3/3 命中，且描述更准确。

### 倒扣的机制

`merge_review` 原有"强制分工"：扫描器启用时丢弃 LLM 输出的
`unverified_as_fact` 与 `conflict_silently_resolved` 两类问题。
丢掉的 4 例正好全部落在这两类：

| 用例 | 目标类型 | LLM 判定 | 结果 |
|---|---|---|---|
| BLD4-INJ-01 / 02 | `unverified_as_fact` | 正确检出 | 被丢弃 → 记为漏检 |
| BLD4-INJ-10 / 11 | `conflict_silently_resolved` | 正确检出 | 被丢弃 → 记为漏检 |

该规则建立在"扫描器在它的领域里比 LLM 可靠"这一前提上。
三次盲测证伪了这个前提。

### 唯一一次门控生效，拦下的是正确报告

A 组对照 42 次运行中扫描器只触发 1 例（确定性，故 3 次），
`BLD4-CLN-08`：

```
原文  客户声称深圳市讯联智能科技有限公司由周启衡实际控制，且无其他对外投资，但未提供可核验依据。
分句  |客户声称…由周启衡实际控制|  |且无其他对外投资|  |但未提供可核验依据|
                                    ↑ 白名单模板在此匹配成功
```

`「客户声称」` 落在**上一个分句**，锚定看不见它。BC-28 的白名单重写解决了
句内管辖，未解决跨句管辖——而穷举跨句形态与穷举句内形态是同一个开放集问题。

## 三次测量的一致方向

| | A 检出 | A 误报 | B 检出 | B 误报 |
|---|---:|---:|---:|---:|
| v3 消融（开发集，2026-08-11） | 100% | 5.6% | 96.7% | 7.5% |
| v2 盲测（2026-08-11） | 63.9% | 36.1% | 71.4% | 8.3% |
| **v4 盲测（本轮）** | **83.3%** | **33.3%** | **97.6%** | **7.1%** |

开发集上扫描器为正贡献，两次未见数据上都是负贡献。
**这是过拟合的标准形态**：扫描器的词表与模板是照着开发集的失败用例逐轮修出来的
（BC-26 补词、BC-27 再补词、BC-28 改判定方向），最终记住的是开发集而不是中文。

## 其余两组结论

1. **结构化清单仍是必要信息源。** C 组关掉清单后 LLM 告警升至 21 条（四组最多），
   误报 38.1%。与 v2 结论一致，这条经受住了第二次盲测。
2. **弱模型不可替代。** D 组 14/14 对照全部稳定误报，等于全部拦截。

## A 组两个稳定失败

- `BLD4-CLN-08`：扫描器误报，即上文的跨分句转述。
- `BLD4-CLN-12`：LLM 告警，但**其批评实质正确**——文本称"尚未取得异常信息只是
  资料现状"，而 EVAL-002 的失信记录、两笔被执行、净利润 -2150 万、负债率 89.1%
  均为**已核实**。这更像 clean 标注不当，不计入系统缺陷，但也不据此调整指标。

## 关于本盲测集独立性的如实声明

- 集合由未参与修复的一方按规格生成，**未读取** `claim_scanner.py`、
  `backend/tests/`、`backend/eval/` 下任何文件。
- 但**生成 prompt 由修复者撰写**，其中"覆盖要求"一节包含了修复者自查时用过的
  若干例句（如「不足以证明不存在」「除非…否则」「客户声称」）。
  因此 **clean 组的良好表现不应全额采信**。
- 相对可信的是两个方向：注入组检出（违规写法未被规定）、
  以及 A/B 差分（同一份文本，措辞偏好对两组同等作用，被差分抵消）。
  删除决定正是基于后者。
- 集合已跑过一次且修复者已读过内容与结果，按协议**退役为回归集**。

## 前一轮（v3）作废记录

`critic_holdout_v3.json`（SHA256 `4d697087…8b3792`）四组已跑，
**全部指标作废**，原因是评测装置错配而非系统缺陷：

- 集合中 14/14 clean 用例使用自创企业名（泊川器械、栖原物流…），
  而装置把文本放进 `based_on` 指定企业的上下文。Critic 正确地报告
  "报告写的不是尽调对象"（`hallucination` critical），却被计为误报。
- 注入组 11 例扫描器职责内的用例中，仅 2 例的目标字段在清单里确为非已核实状态；
  其余 6 例字段为已核实（扫描器正确跳过被记为漏检）、3 例不涉及清单字段。

根因是生成 prompt 只写了"全部虚构"，漏了"必须与 based_on 企业一致"。
与 BC-12、BC-14 同形：**指标极端时先质疑测量装置**。已记为 BC-47 的前置发现。
